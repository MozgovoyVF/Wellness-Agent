# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Команды

```bash
npm run dev      # http://localhost:3000
npm run build    # сборка + проверка типов (отдельного tsc-скрипта нет)
npm start        # прод-сервер поверх сборки

npm run ingest                     # knowledge/*.md → эмбеддинги → таблица knowledge_chunks
npm run replay runs/run-XXX.json   # переиграть прогон и сравнить с трейсом
npm run eval                       # 9 кейсов из evals/cases, таблица PASS/FAIL
npm run eval low-energy            # только названные кейсы
npm run mcp:inspect                # тулы и ресурсы всех серверов конфига, как их видит клиент
npm run mcp:inspect -- --read      # плюс содержимое каждого ресурса
npm run mcp:inspect -- --module recipes   # что из тулов отнимает модуль OS
```

`mcp:inspect` — дешёвая проверка после правок в `src/mcp/`: он поднимает те же серверы
тем же способом, что и харнесс, но в модель не ходит вовсе, поэтому стоит секунды
и ничего не тратит. Если сервер не стартует или тул потерялся, видно сразу и без прогона.
**Это же единственная проверка политики доступа:** у каждого тула напечатано
«коучу: да / нет / после approve» — то есть ровно то, что даст `toolFilter` из конфига.
Опечатку в `tools` или `writeTools` больше ничем не поймать.

Внешние серверы там тоже поднимаются, поэтому команда ходит в сеть (`npx`) и на первом
запуске занимает десятки секунд. Недоступный сервер печатает «не поднялся» и не мешает
показать остальные.

**Тулы скрипт не зовёт никогда, ресурсы читает только по `--read`.** Среди тулов есть
`save_health_plan`, `append_daily_log`, `check_habit`, `update_preferences` и `write_file`:
«посмотреть сервер» не должно переписывать `data/`.
У чтения ресурса побочных эффектов нет по определению, и флаг там стоит только ради
читаемости вывода. Ресурсы — единственное, что этой командой вообще проверяется на деле:
`plans://latest` умеет отвечать, когда `data/output.md` ещё нет, и проверяется это так —

```bash
mv data/output.md data/output.md.bak && npm run mcp:inspect -- --read
mv data/output.md.bak data/output.md
```

Тестов, линтера и CI в проекте нет — единственная автоматическая проверка это
`npm run build`, он же гоняет TypeScript. `npm run eval` — не замена: это девять настоящих
заходов в модель, десятки минут и расход ключа, и запускают его руками после правки
промптов, а не на каждое изменение.

`npm run ingest` — разрушающая операция: очищает `knowledge_chunks` и заливает заново.
В этом и состоит требуемая идемпотентность, но правки, сделанные в базе руками, он сотрёт.
Ходит в OpenAI за эмбеддингами и в Postgres — то есть тратит ключ и требует настроенной БД.

Нужен `.env` в корне с `DEEPSEEK_API_KEY` и `DEEPSEEK_MODEL`. Без ключа приложение
собирается и открывается, но любой прогон возвращает `500` — ключ проверяется лениво,
при первом обращении к агентам.

Базе знаний нужны ещё три переменные: `OPENAI_API_KEY`, `EMBEDDING_MODEL` и
`SUPABASE_DB_URL`. Ключ именно OpenAI, а не DeepSeek: **эндпоинта эмбеддингов
у DeepSeek нет вовсе**, поэтому у RAG отдельный провайдер и отдельный baseURL. Без них
прогон не падает — тул поиска отвечает «база знаний недоступна», и коуч дописывает план
по профилю и дневнику.

Проверять изменения в агентах удобнее через API, а не через браузер. Роутов два, и брать
стоит тот, который проверяешь:

```bash
# не-стрим: один JSON в конце. Им же ходят evals и replay.
curl -s -X POST http://localhost:3000/api/agent/run \
  -H 'Content-Type: application/json' -d '{"task":"составь ужин на сегодня"}'

# стрим: тот же прогон, но видно ход работы. -N обязателен, иначе curl буферизует.
curl -s -N -X POST http://localhost:3000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"id":"1","role":"user","parts":[{"type":"text","text":"составь ужин на сегодня"}]}]}'
```

Стрим отдаёт SSE, и глазами он нечитаем — интересны только части `data-step` и `data-result`:

```bash
… | grep '^data: ' | sed 's/^data: //' | jq -c 'select(.type|startswith("data-"))'
```

Полный прогон — от 20 секунд до нескольких минут: каждый раунд это два похода в модель.

## Архитектура

Четыре агента, но цикл управляет только тремя: триаж решает, стоит ли вообще браться,
коуч пишет план, ревьюер его судит. Четвёртый, роутер намерения, работает до цикла
и внутри него не участвует — он одним дешёвым заходом выбирает модуль, которым цикл
дальше воспользуется (раздел «OS» ниже). Главный принцип: **оркестрация живёт в коде,
а не в промптах**. Сколько будет раундов, где стоит порог одобрения и что делать
с вердиктом, решает цикл в [src/harness/runHealthAgent.ts](src/harness/runHealthAgent.ts);
промпты про это не знают и знать не должны.

```
app/page.tsx (server)  →  app/chat.tsx (client, useChat)
                              ↓ POST /api/chat            ← стрим, интерфейс ходит сюда
                              ↓ POST /api/agent/run       ← не-стрим, жив для скриптов и страховки
                          runOS(task, { onEvent? })
                              ↓
                          classifyIntent(task) → модуль + confidence → событие 'module'
                              ↓
                          runHealthAgent(task, { module, intentConfidence, minRounds, maxRounds, onEvent? })
                              ↓
                          triage(task) → HUMAN? → прогон закончен, раундов ноль
                              ↓ WELLNESS
                          поднять MCP-серверы из servers.config.ts (процессы, stdio)
                          с toolFilter = политика конфига ∩ список модуля
                              ↓
                          coach ⇄ MCP-серверы + src/skills/ + src/rag/ → reviewer → вердикт → (revise? назад к coach)
                                                                          ↓ approve
                                          гейт открыт → закрепляющий заход коуча
                              ↓
                          закрыть MCP-серверы (finally)
                              ↓
                          approve? → updateMemory(): append_daily_log + update_preferences мимо агента
```

Наружу прогон рассказывает о себе двумя способами, и они не дублируют друг друга.
**Что получилось** — это `HealthAgentResult`, возвращаемое значение; до конца цикла его
нет. **Что происходит прямо сейчас** — это события `onEvent`, и ответ на них нужен раньше,
чем появится значение. Отсюда два роута: `/api/agent/run` ждёт результата и отдаёт JSON,
`/api/chat` подписывается на события и стримит их по мере поступления.

**Раундов не меньше минимума и не больше максимума.** `approve` закрывает цикл, только
когда минимум пройден; до тех пор одобренный план возвращается коучу на усиление. Раунд
добора может выйти хуже, поэтому наружу уезжает не последний раунд, а итоговый —
последний одобренный, иначе последний бывший (`finalRound` в `score.ts`). Так добор
может результат только улучшить.

`runHealthAgent` — оркестратор: он собирает клиент, промпты, агентов и цикл, а всё
остальное разложено по модулям `src/harness/` — по одной ответственности на файл.
Роут только валидирует тело и превращает исключения в `500`; страница и консоль ничего
не решают. Харнесс не импортирует ничего из Next — только `node:fs`, `@openai/agents`
и `zod`, — и это стоит сохранить.

| Модуль | Отвечает за |
|---|---|
| `runHealthAgent.ts` | триаж, цикл, гейт, порог одобрения, календарь и контекст ревьюера, закрепляющий заход, жизнь MCP-серверов, сборка результата |
| `triage.ts` | разбор односложного ответа триажа, `TriageVerdict { blocked, reason }` |
| `validateReview.ts` | Zod-схема ревью, `score` из `breakdown`, снятие ```` ```json ````-ограждения, один ретрай |
| `rounds.ts` | `RoundState { round, plan, review }`, накопление истории, `redactPlans` |
| `score.ts` | `finalRound` (последний `approve`, иначе последний) и `improvedAcrossRounds` |
| `calendar.ts` | `calendarBlock(now)` — сегодняшняя дата и ближайшие дни с днями недели |
| `promptVersions.ts` | `ACTIVE_PROMPTS` и загрузка `prompts/<агент>.<версия>.md` |
| `toolCalls.ts` | `collectToolCalls`: разбор `newItems` из SDK после захода |
| `events.ts` | `AgentEvent` и `createEmitter(onEvent?)` — рассказ о ходе прогона |
| `streamCoach.ts` | `runCoach`: заход коуча стримом (когда есть слушатель) или обычным `run` |
| `traceRun.ts` | запись прогона в `runs/run-<время>.json`, формат `RunTrace` |

Тулы коуча собираются в `runHealthAgent`, а не в `src/skills/`: массив локальных навыков
и тул поиска по базе знаний — разные ответственности и разные источники, и складывать их
в один модуль значило бы стереть границу. Что коучу доступно, и так решает харнесс.

Модули `validateReview` и `triage` не знают про агентов: как спросить модель, им передаёт
оркестратор коллбэком (`AskReviewer`, `AskTriage`). Так политика ретрая живёт отдельно от SDK.

**Промпты лежат в `prompts/`, а не в коде.** Агенты стали фабриками
(`createCoach(instructions, tools, mcpServers)`), текст в них приходит снаружи. Чтобы
попробовать другую редакцию, кладут файл `healthCoach.v9.md` и меняют версию
в `ACTIVE_PROMPTS` — правок в коде агентов и харнесса это не требует. Файл читается на каждый прогон, так что
правка промпта подхватывается без перезапуска.

**Данные коуч добывает сам, тулами, и источников у тулов два.** Всё, что про данные
человека, отдаёт собственный MCP-сервер в отдельном процессе; локальными обёртками
`tool()` остались два навыка, где данных человека нет вовсе.

Серверов четыре, и три из них — готовые пакеты из npm (`filesystem`, `weather`, `notion`),
подключённые записью в `src/mcp/servers.config.ts` без единой строки кода интеграции.
Обёрток над чужими тулами нет: агент получает их как есть.

**Деление не случайное, и оно же — предмет урока.** В MCP уехало ровно то, что про
данные человека: чтобы взять их, нужен интерфейс наружу, и стандартный протокол его даёт —
подключиться может любой MCP-клиент, а не только это приложение. Локальными остались
шаблоны тренировок (зашиты в код) и список покупок (разбор текста, который коуч только
что написал сам): чужого источника данных там нет, и сервер ради чистой функции заводить
незачем. Контраст оставлен намеренно — в трейсе оба вида тулов стоят рядом, и видно,
что **для агента разницы нет**: SDK превращает MCP-тулы в такие же вызовы функций.

| Модуль | Отвечает за |
|---|---|
| `src/mcp/markdownHealthServer.ts` | сам сервер: 8 `registerTool`, 6 `registerResource`, stdio |
| `src/mcp/servers.config.ts` | `MCP_SERVERS`: какие серверы поднимать и что из них давать коучу |
| `src/mcp/connectServers.ts` | `connectMcpServers(gate)` — подъём всех включённых, `toolFilter` из конфига, карта «тул → сервер»; `connectMcpServer(name)` — подъём одного, без гейта и фильтра |
| `src/mcp/toolNames.ts` | `MCP_TOOLS`, `NOTION_TOOLS` и `MCP_RESOURCES`: имена, объявленные один раз |
| `src/mcp/notionPage.ts` | `saveToNotion(markdown)` — страница в Notion мимо агента, для кнопки под планом |
| `src/mcp/markdownBlocks.ts` | `toNotionBlocks(markdown)` — план в блоки Notion |
| `src/skills/index.ts` | `localCoachTools(gate)` — литеральный массив из двух тулов |

**Реестр серверов — данные, а не код.** `connectServers` не знает ни одного сервера
по имени: он фильтрует `MCP_SERVERS` по `enabled`/`requiresEnv`, строит на каждый
`MCPServerStdio` с `toolFilter` из полей `tools`/`writeTools` и складывает карту
источников из `listTools()` каждого сервера. Поэтому **добавление сервера — запись
в конфиге, ноль правок в харнессе**, а новый сервер получает свой префикс в трейсе сам.
Прежний `src/mcp/healthMcp.ts` удалён: держать первый сервер по-старому, а остальные
по-новому означало бы, что тезис неверен для первого же сервера.

`listTools()` отдаёт полный список сервера, **без** `toolFilter` (фильтр SDK применяет
позже, на стороне раннера) — поэтому карта источников полна и во время закрытого гейта.

Файлы сервер сам не читает: он зовёт те же чистые функции из `src/skills/`, что и до
переезда, — у `data/` остался один способ доступа, а не два разошедшихся. Те же функции
харнесс зовёт напрямую, когда кладёт профиль и дневник в контекст ревьюера: это не тул
агента, а сборка входа, и идти за ней через MCP незачем.

**Серверы — процессы, и владеет ими харнесс.** Поднимаются после триажа, перед первым
раундом, параллельно (`Promise.all`), закрываются в `finally` вокруг цикла через
`Promise.allSettled` — упавший `close` одного не повод оставить висеть остальные. После
триажа, а не в начале: заблокированный прогон не должен платить за запуск процессов.
Команда запуска у своего сервера — `process.execPath` + `node_modules/tsx/dist/cli.mjs`,
а не `npx tsx`: путь детерминированный и не тратит время прогона. У внешних выбора нет,
там `npx -y` с прибитой версией. `cwd` передаётся явно, иначе дочерний процесс не найдёт
`data/`.

**В MCP уехал только доступ к данным и инструментам.** Оценка, валидация ревью, порог
одобрения и порядок раундов остались в харнессе; серверы не знают про прогон ничего,
в том числе одобрен ли план. По той же причине политика гейта живёт в `servers.config.ts`,
а не внутри сервера: это не про данные, а про прогон.

| Модуль | Отвечает за |
|---|---|
| `src/os/runOS.ts` | весь поток OS: роутинг, прогон, память; шапка держит инвариант про ревьюера |
| `src/os/router.ts` | `classifyIntent`, `MODULE_CONFIDENCE`, `moduleCatalog`; любая осечка → general |
| `src/os/memory.ts` | `updateMemory`: две записи после approve, обе через MCP мимо агента |
| `src/os/preferenceSignal.ts` | маркеры «запомни / понравилось», чистая функция без модели |
| `src/os/modules/types.ts` | тип `Module` и `ALWAYS` — тулы, которые есть у каждого модуля |
| `src/os/modules/index.ts` | `MODULES`, `GENERAL`, `moduleByName`; здесь же записан инвариант |
| `src/agents/intentRouter.ts` | `createRouter(instructions)` — агент без тулов, своя модель |

**Памятей у коуча две, и это главное различие в проекте.** `data/profile.md` и `data/log.md` —
личная память: кто человек и что с ним происходило. Она достаётся **целиком и точно**,
тулами MCP-сервера, потому что профиль надо прочитать весь, а не «пять похожих кусков».
`knowledge/*.md` — база знаний: что коуч вообще умеет предложить кому угодно. Она уезжает
в Postgres векторами и достаётся **по смыслу запроса**, топ-5 секций. Разница не в формате
хранения, а в вопросе: личная память отвечает «про кого план», база знаний — «из чего его
собрать». Поэтому `data/recipes.md` и `knowledge/recipes.md` — **не дубликаты**: первый
про то, что человек правда готовит, второй про то, что мы умеем. Переносить `profile`
или `log` в базу нельзя: точное чтение там не заменяется приблизительным поиском.

| Модуль | Отвечает за |
|---|---|
| `src/rag/chunks.ts` | `readKnowledgeChunks()` — разбор `knowledge/*.md` по `##`; `embeddableText()` |
| `src/rag/embed.ts` | `embed(texts)` — один fetch в OpenAI-совместимый `/v1/embeddings` |
| `src/rag/store.ts` | `pg`-пул, `replaceChunks` (одной транзакцией), `matchChunks` (`<=>`), `closePool` |
| `src/rag/retriever.ts` | `searchKnowledge(query, topK)` — embed запроса и поиск, больше ничего |
| `src/rag/retrievalLog.ts` | `createRetrievalLog()` — журнал обращений на прогон, форма как у гейта |
| `src/rag/searchKnowledgeTool.ts` | обёртка `tool()`: описание, форматирование выдачи, запись в журнал |
| `docs/001_create_knowledge_chunks_table.sql` | расширение `vector`, таблица, индекс по файлу |
| `docs/002_create_knowledge_embedding_index.sql` | `ivfflat` — выполняется **после** первого ингеста |
| `scripts/ingest.ts` | `npm run ingest`: chunks → эмбеддинги → перезалив таблицы |

**Chunk — это одна `##`-секция целиком**, а не N символов с перекрытием. Границы выбирал
человек заголовками, поэтому найденный кусок не обрывается посреди состава блюда. Всё,
что стоит до первой `## ` в файле, отбрасывается: это название документа, а не знание.

**В вектор при этом уходит не весь chunk, а заголовок и первый абзац** (`embeddableText`).
Эмбеддинг усредняет весь текст, и длинный хвост глушит заголовок: у рецепта хвост — список
граммов, семантически почти пустой. С полным телом запрос «ужин с высоким белком без
молочки» не находил **ни одного** рецепта ужина в топ-5, а «Треска с чечевицей — ужин
с высоким белком, без молочки» стояла тринадцатой, ниже завтраков. С первым абзацем —
5 из 5 рецептов, лосось первым с 0.63 вместо 0.36. Замеры и цифры лежат в комментарии
к функции. Коучу при этом едет **весь** chunk: урезан только вектор.

**Reranking, hybrid search и переписывания запроса здесь нет намеренно.** `searchKnowledge`
делает ровно два шага — один embed, один similarity search. Каждое «мелкое улучшение»
добавляет ещё один поход в модель и ещё одно место, где выдача меняется незаметно.

**Тул локальный, хотя источник данных чужой** — осознанное отступление от принципа выше
(«чужой источник → MCP-сервер»). Причины две: журнал retrieval через границу процесса
не прокинуть, а заголовки найденного обязаны попасть в трейс; и сам поиск не про данные
человека, а про общее знание. Гейта у тула нет — он только читает.

**Запрос и заголовки найденного едут отдельным полем `retrievals`**, а не выуживаются
из `newItems`. `collectToolCalls` отдаёт только имена тулов, и достать остальное можно
лишь разбором внутренностей SDK с парсингом JSON конкретного тула — а `toolCalls.ts`
намеренно единственное место, где харнесс о них знает. Журнал создаётся в `runHealthAgent`
рядом с гейтом и по той же идиоме: харнесс владеет, тул пишет.

**Отказ базы знаний прогон не роняет.** Нет `SUPABASE_DB_URL`, база недоступна, таблица
пуста — тул возвращает текст «база знаний недоступна» и пишет в журнал запись с пустым
списком. Та же логика, что у `LOCKED_MESSAGE` в гейте: отказ инструмента не повод бросать
работу. Запись в журнал при ошибке делается обязательно — иначе неудачная попытка
выглядела бы в трейсе как отсутствие попытки.

Описания тулов — часть интерфейса модели, а не комментарий: по ним коуч решает, звать ли
навык. Правишь описание — правишь поведение агента ровно так же, как правкой промпта.
Для MCP-тулов описания живут в `registerTool` на сервере.

**Ресурсы агенту не достаются.** `profile://me`, `logs://recent`, `recipes://all`,
`plans://latest`, `habits://all`, `preferences://all` — вторая половина протокола. Agents
SDK превращает в тулы агента только `tools`; ресурс надо запросить явно через
`readResource`, и коуч этого не делает. Они здесь ради `npm run mcp:inspect` и MCP
Inspector — показать сервер целиком, все шесть штук. Профиль приезжает коучу тулом
`read_profile`, а не по адресу `profile://me`.

**Ревьюеру и триажу тулов не даётся никогда — ни локальных, ни MCP.** Оба — контур
безопасности, и их единственный результат обязан быть вердиктом: агент, способный писать
файлы, оставит след от плана, который сам же завернул. MCP-сервер подключается только
к коучу (`createCoach(..., [mcp])`); `createReviewer` и `createTriage` про него не знают,
и подключать его туда «чтобы ревьюер сам достал дневник» — та же ошибка, что дать им
`savePlan`. Профиль, дневник и задачу ревьюеру кладёт в контекст харнесс —
`REVIEWER_LOG_DAYS` заведомо больше, чем возьмёт коуч, иначе ревьюер завернёт как выдумку
факт из дня за границей окна. Промпт ревьюера обязан описывать этот вход честно: версия v5
утверждала, что задачи не видит, — и перестала ставить `needs_human_professional` по сути
запроса, потому что вердикт про запрос, а смотрела она только на план.

**День недели считает код, а не модель.** `calendarBlock()` кладёт в начало входа коуча
и ревьюера сегодняшнюю дату и неделю вперёд с подписанными днями. Причина не в том, что
модель не знает календарь — спрошенная в лоб, она отвечает верно, — а в том, что посреди
написания плана она делает это попутно и ошибается: два прогона подряд назвали 18 и 19
августа понедельником и вторником вместо вторника и среды. Своего источника дат у агентов
нет вовсе: тул погоды отдаёт голый ISO (`2026-08-19`), задача говорит «на завтра».
Промптом это не чинится по той же причине, что и гейт: «считай правильно» — просьба.
Календарь считается **один раз на прогон** и общий у коуча с ревьюером — иначе у них
разъехалось бы «сегодня». Сверка плана с ним стоит у ревьюера **блокирующей проверкой**
(шаг 2), а не осью: ось сделала бы шкалу шестибалльной и поехала бы разметка.

**Триаж стоит до коуча и видит только задачу.** Решение «нужен живой специалист» относится
к запросу, поэтому и спрашивается оно про запрос, отдельным коротким заходом (`triage.v1`,
ответ в одно слово — `WELLNESS` или `HUMAN: причина`). Ревьюер, который видит план, обелить
запрос легко: грамотный отказ коуча читается как хороший план, и ровно так был пропущен
запрос про дозировки при болях в груди — `runs/run-2026-08-17T08-38-34-265Z.json`. У триажа
плана нет, обелять нечем. Заблокированный прогон стоит одного похода в модель вместо целого
цикла: 2 секунды против 76.

Контура два, и это не дублирование: ревьюер ставит `needs_human_professional` по сути
запроса самостоятельно (шаг 1 в `safetyReviewer.v8`). Поэтому **непонятный ответ триажа
пропускает задачу дальше, а не блокирует её** — за ним есть кому поймать, а осечка в другую
сторону отказывала бы человеку в ужине из-за одного сбойного ответа модели.

**Гейт на запись — в коде, а не в промпте.** `createGate()` из `src/skills/gate.ts` закрыт
весь цикл. Харнесс открывает гейт после `approve` и делает **закрепляющий заход** —
отдельный вызов коуча «план одобрен, сохрани». Промптом это не решается: промпт — просьба,
а не гарантия, модель может сохранить черновик «на всякий случай», и неодобренный план
ляжет в `output.md`. Список покупок стоит под тем же гейтом по той же причине, что работает
`redactPlans`: продукты из плана, записанные в `shopping.md`, — это тот же план, только сбоку.

**Политика одна, а исполняется двумя способами — потому что тулы живут в разных процессах.**

| Тул | Как держится гейт | Что видит модель до `approve` |
|---|---|---|
| `generateShoppingList` (локальный) | `gate.isUnlocked()` внутри `execute` | тул есть, вызов возвращает `LOCKED_MESSAGE` |
| `save_health_plan` (MCP) | `writeTools` в конфиге → `toolFilter` | тула нет в списке вовсе |
| `write_file` (MCP, чужой сервер) | там же | тула нет в списке вовсе |

**Гейт распространяется и на чужие серверы, иначе он декоративный.** `write_file` из
`filesystem` пишет на диск ровно так же, как наш `save_health_plan`, и коуч положил бы
неодобренный план в `plans/` в обход ворот. Поэтому политика записи объявляется в конфиге
полем `writeTools` — по одному списку на сервер, — а `connectServers` собирает из него
`toolFilter`. Оговорка: у копии в `plans/` **нет** текстовой сверки, какая есть
у `output.md` (см. ниже) — она потребовала бы обёртки над чужим тулом. Авторитетная копия
плана всегда `data/output.md`.

Локальному тулу хватает замыкания, а MCP-тул исполняется в чужом процессе, куда замыкание
не дотянется. Единственная точка перехвата на нашей стороне — `toolFilter`: он решает,
попадёт ли тул в список, который увидит модель, и перевычисляется на каждый заход агента.
Так один и тот же объект переживает и цикл (гейт закрыт), и закрепляющий заход (открыт).
Получилось строже прежнего отказа — позвать то, чего в списке нет, модель не может, — и
политика при этом осталась в коде харнесса: **сервер про одобрение по-прежнему не знает**
и записал бы, если бы его позвали. Прятать её внутрь сервера было бы ошибкой: это не про
данные, а про прогон.

Тем же фильтром коучу **никогда** не даются `append_daily_log` и `update_preferences`:
их просто нет в списке `tools` у `markdown-health`. Дневник — источник фактов, на который
опирается ревьюер, проверяя план на выдумки; коуч, дописывающий туда во время
планирования, подделывает собственную доказательную базу. Предпочтения — то, что
подтвердил человек, а не то, что решила модель, и решение писать их принимает харнесс
(`src/os/memory.ts`), а не коуч. Сервер оба тула при этом отдаёт — они видны в
`npm run mcp:inspect`, и в этом весь смысл: у сервера восемь тулов, коучу постоянно
видны пять (`read_profile`, `read_recent_logs`, `list_recipes`, `read_habits`,
`check_habit`), и после одобрения к ним добавляется шестой — `save_health_plan`.
Ровно так же `filesystem` отдаёт четырнадцать, а коуч видит три — `edit_file`, `move_file`
и остальное в `tools` не вписаны.

**У кнопки «в Notion» гейта нет — у неё сверка с диском.** Под одобренным планом стоит кнопка,
которая кладёт его страницей внутрь `Wellness`: это для случая «сохранить забыл попросить,
а хочется». Роут `app/api/plan/notion/route.ts` зовёт `saveToNotion()`, а тот поднимает
**один** сервер (`connectMcpServer('notion')`) и дёргает `API-post-search` и `API-post-page`
напрямую — **модели в этом пути нет вовсе**: решать нечего, план уже написан и одобрен, надо
исполнить. Гейт сюда не годится принципиально: он живёт ровно столько, сколько прогон, а
кнопку жмут после. Его роль играет `planMatchesDisk()` — присланный текст обязан совпасть
с `data/output.md`, иначе `409`. Файл пишется только после `approve`, поэтому совпадение
с ним и есть доказательство одобрения; без этой проверки роут был бы дыркой в воротах
(«отправь в Notion любой текст»), и гейт стал бы декоративным. Флагу от клиента здесь
верить нечему, поэтому сверка по тексту.

Кнопка показывается по трём условиям сразу, и все три берутся из `HealthAgentResult`:
вердикт `approve`; `API-post-page` есть в `toolSources` (сервер поднимался — значит,
`NOTION_TOKEN` настроен); `API-post-page` нет в `toolCalls` (агент уже сохранил сам —
второй копии не надо). `toolFilter` этому пути не мешает и не помогает: он решает только
то, что видит модель в списке тулов, а прямой `callTool` идёт мимо него — поэтому
`connectMcpServer` фильтр и не ставит.

После закрепляющего захода харнесс сверяет `data/output.md` с `final.plan` **по тексту, а не
по факту вызова**: коуч охотно зовёт `save_health_plan`, но передаёт в него план своими
словами — короче, приглаженный, без куска. Не совпало (или тул не позвали вовсе) — харнесс
перезаписывает файл сам, той же чистой функцией `savePlan()`, что зовёт и сервер, и говорит
об этом в лог. Идти ради дописки через MCP незачем. Это страховка, а не обход: гейт уже
открыт, план уже одобрен. В `toolCalls` дописка не появится — трейс не должен выглядеть
так, будто агент справился сам.

**DeepSeek подключён подменой клиента** в `configureClient()`: OpenAI-совместимый клиент
с другим `baseURL`, принудительно `chat_completions` (Responses API у DeepSeek нет)
и выключенный трейсинг (он шлёт данные в OpenAI). Настройка ленивая и однократная —
на сервере отсутствие ключа должно быть ошибкой запроса, а не падением процесса.

**Ревьюер отдаёт сырой JSON, а не structured output.** Поэтому есть `parseReview`:
снимает ```` ```json ````-ограждение, валидирует Zod-схемой и возвращает `null` при любой
неудаче. `validateReview()` даёт ровно один ретрай с напоминанием о схеме, после чего
бросает — две неудачи подряд это поломка, а не случайность.

**`score` модель не называет — его складывает харнесс** из `breakdown`, пяти осей по 0–2.
Модель, которой доверили и оценку, и её обоснование, ставит одно, а обосновывает другое,
и разойдясь, эти два числа никем не сверяются. Поэтому `score` в схеме ответа нет вовсе:
`parseReview` считает сумму сам. По той же причине порог одобрения держит код —
`enforceApproveThreshold` понижает `approve` со `score` ниже `APPROVE_SCORE` до `revise`
и, если замечаний при одобрении не было, дописывает одно: иначе коуч получит «устрани
каждое замечание» с пустым списком.

**`HealthAgentResult` — общий контракт** между харнессом и UI. Клиентский компонент тянет
его через `import type`, поэтому серверный модуль в браузерный бандл не попадает. Кроме
`plan` и `review` в нём едут данные о самом прогоне: `rounds` (история всех раундов),
`finalRound` (номер раунда, чей план уехал наружу), `finalScore`, `improved`, `toolCalls`
(имена вызванных тулов по порядку, со всеми повторами и по всем раундам), `retrievals`
(обращения к базе знаний: запрос и заголовки найденного), `promptVersions`
и `durationMs`. UI показывает их свёрнутым блоком `.trace` в подвале сообщения — это
машинные данные, вердикт должен читаться раньше; список тулов идёт там же под заголовком
«что сделал агент».

## Стриминг: как прогон рассказывает о себе, пока идёт

**Событий понадобилось ровно потому, что результат опаздывает.** `collectToolCalls`
вызывается *после* захода коуча — значит, имена тулов физически появляются одной пачкой
через минуту после того, как коуч их позвал. Для трейса это неважно, для живого таймлайна
это разница между «оживает по мере работы» и «стоит, потом всё разом». Поэтому
`runHealthAgent` принимает необязательный `onEvent` и рассказывает о себе по ходу:
`triage`, `round-start`, `tool`, `plan-delta`, `review-start`, `review-done`, `finalize`.

**Варианта `done` в `AgentEvent` нет намеренно.** Итог — это возвращаемое значение, и
описывать его вторым способом значило бы завести два контракта на одно и то же. Роут
делает `await runHealthAgent(...)` и берёт итог оттуда.

**`createEmitter(onEvent?)` без обработчика возвращает пустой `send`.** Поэтому в цикле
нет ни одного `if (onEvent)`: код читается одинаково для evals и для чата, а расхождение
поведения между ними невозможно по построению, а не по внимательности. Исключение
слушателя гасится — упавший рендер строки таймлайна не повод ронять прогон, который стоит
минуту работы и денег за ключ.

**`emitter.active` читает ровно один модуль — `streamCoach`.** Нет слушателя — заход идёт
прежним `run(coach, input, { maxTurns })`, тем же вызовом, что стоял в цикле до всего
этого; по нему ходят evals, replay и `/api/agent/run`. Есть слушатель — `run(..., { stream: true })`
и разбор `RunStreamEvent`: `tool_called` даёт живой вызов тула вместе с его аргументами,
`raw_model_stream_event` с `output_text_delta` — текст плана по кускам. Возврат в обоих
случаях одной формы (`newItems`, `finalOutput`), поэтому цикл не знает, каким путём пришёл
ответ, и не должен знать.

**Фильтр дельт — по типу события, а не по наличию поля `delta`.** Рядом в том же потоке
идут сырые провайдерские события (`type: 'model'`), которых на порядок больше: на 53
`output_text_delta` приходится 143 таких. Утиная типизация утащила бы в план их содержимое.

**Дельты — это черновик, а не план.** Наружу уезжает `finalRound` — последний одобренный
раунд, а он не обязан быть последним. Поэтому текст, собранный из дельт, живёт только
в строке таймлайна живым превью, а в сообщение чата план стримится **после** цикла и
берётся из `result.plan`. Так текст сообщения всегда ровно тот, что признан итогом, —
по построению, а не по совпадению.

| Модуль | Отвечает за |
|---|---|
| `app/api/chat/route.ts` | `createUIMessageStream`, перевод `AgentEvent` → `data-step`, стриминг плана |
| `app/chat-protocol.ts` | `Step`, `ResultData`, `WellnessUIMessage`, `stepIds` — контракт роута и консоли |
| `app/chat.tsx` | `useChat`, таймлайн, план, вердикт, трейс, сессия прогонов |

**Контракт потока вынесен в отдельный модуль, а не описан дважды.** Роут и консоль иначе
описывали бы форму сами, и разъехавшись, дали бы молча пустой таймлайн: TypeScript
о расхождении не узнал бы. `chat-protocol.ts` обязан оставаться типами и константами —
он импортируется клиентским компонентом, и любая исполняемая строка оттуда уедет
в браузерный бандл.

**Шаг таймлайна пишется целиком, а не патчем.** Запись data-части с тем же `id` заменяет
данные, а не сливает их, поэтому `createStepWriter` держит карту состояний и на каждое
обновление шлёт шаг со всеми полями. Без неё «дописать статус» стирало бы `phase` у плана
и `tool` у вызова.

**Превью черновика троттлится 150 мс, и сбрасывается принудительно на конце раунда.**
Перезаписывать его на каждую дельту нельзя — часть заменяется целиком, и план в 3 КБ
при посимвольных дельтах вылился бы в сотни килобайт на воздух. Принудительный сброс
нужен, чтобы последние дельты, пришедшие внутри окна, не потерялись на самом видном
месте — на последних строках плана.

**Готовый план режется по строкам, а не по символам.** `app/plan-markdown.tsx` разбирает
markdown построчно, и посимвольный стрим показывал бы `#` и `**` сырыми до конца строки.

**Памяти между прогонами у агента нет.** `runHealthAgent(task: string)` истории
не принимает, и роут читает только последнее сообщение человека. Склеить транскрипт
в `task` было бы единственным способом дать память — но `task` уезжает не только коучу:
он идёт в `## Задача` ревьюеру, по нему судит триаж, и он целиком пишется в трейс.
Транскрипт в поле задачи прошёл бы прямо через оба защитных контура. История прогонов
поэтому живёт только на экране: сессия копит сообщения, кнопка «новая сессия» их сбрасывает,
перезагрузка страницы — тоже.

**Прогон остаётся на диске.** `traceRun` вызывается из `finish()` в `runHealthAgent` —
единственной точки, где собирается `HealthAgentResult`, поэтому трейс пишут оба выхода,
включая защитный контур, и строка вызова одна. Ошибка записи ловится внутри `traceRun`
и не роняет прогон: план уже составлен и проверен, терять его из-за служебного файла нельзя.
Планы в трейсе урезаны до 500 символов — он для чтения и диффа, а не хранилище планов.
Специальной ветки под `needs_human_professional` в `traceRun` нет и не нужно: история
приезжает уже после `redactPlans`, и защитный контур доезжает до диска сам.

Поверх трейсов живут два скрипта на `tsx`, оба вне Next: `scripts/replay.ts` (переиграть
задачу из трейса и показать «было / стало») и `scripts/eval.ts` (девять кейсов из
`evals/cases/*.json`, простой `for…of`, PASS/FAIL). Оба первым импортом тянут
`scripts/env.ts` — он зовёт `process.loadEnvFile()`, потому что вне Next `.env` читать
некому, а порядок важен: тела импортированных модулей выполняются раньше тела скрипта.
Правило «какой раунд считается итоговым» скрипты не повторяют — `finalRound` в `score.ts`
обобщён по типу раунда, чтобы его же мог звать replay на раундах из трейса.

### Три вердикта определяют всё поведение

| Вердикт | `plan` в ответе | Гейт | `data/output.md` | Что дальше |
|---|---|---|---|---|
| `approve` | текст плана | открывается | перезаписывается | цикл выходит, если пройден `minRounds`, иначе новый раунд «усиль план» |
| `needs_human_professional` | `null` | остаётся закрыт | не трогается | цикл выходит сразу, минимум и прошлые одобрения не в счёт |
| `revise` | текст плана | остаётся закрыт | не трогается | новый раунд, до `maxRounds` |

`needs_human_professional` приезжает из двух мест: от триажа — тогда раундов ноль, коуч
не запускался, `rounds` пустой и `finalRound` равен нулю, а MCP-сервер даже не поднимался;
и от ревьюера — тогда раунды есть, но их планы вычищены `redactPlans`. UI обе формы
переживает: где нет плана, там вместо оценки и числа раундов прочерк.

`output.md` пишется один раз, в закрепляющем заходе после цикла, а не в момент одобрения:
одобренных раундов при доборе бывает несколько, а лечь в файл должен ровно тот план,
что уехал наружу. Пока гейт закрыт, на диск не ложится ничего — ни план, ни список покупок.

`needs_human_professional` ставится по сути запроса, а не по качеству плана, и план при
нём наружу не отдаётся — это защитный контур, не деталь отображения. **История раундов
подчиняется тому же контуру:** перед возвратом она проходит через `redactPlans`, иначе
план утёк бы в `rounds[].plan` в обход `plan: null`. Исход «раунды кончились, одобрения
нет» возвращает последний план с вердиктом `revise`; UI показывает его с пометкой, что
он не одобрен и не сохранён.

## Что легко сломать

- **Рубрика ревьюера обязана требовать больше, чем требует формат коуча.** Это главный
  урок v7 → v8. Формат коуча мандатит ссылку на дневник, граммы и раздел «На что смотреть»;
  рубрика v7 давала за ровно это по 2 балла. В итоге четыре оси из пяти были прибиты
  к двойке конструктивно, пятая (`safety`) — к единице, потому что требовала «триггеров
  обращения к врачу», а такого раздела коучу писать никто не поручал. Минимум шкалы стал
  равен `APPROVE_SCORE`, и понижение не сработало **ни разу за 39 прогонов**. Правишь
  формат коуча — перечитай оси; правишь оси — перечитай формат.
- **Ось, которую артефакт не может удовлетворить, — это не строгость, а константа.**
  `safety` четыре месяца снимала ровно один балл у всех и потому не различала ничего.
  Постоянный штраф просто сдвигает шкалу; разброс он не создаёт.
- **Убрав число из промпта, легко вернуть его обратно.** С v8 планка названа один раз —
  в `APPROVE_SCORE`. Пока она стояла и в промпте, модель считала сумму сама и подгоняла
  оси под неё. Напишешь в промпте «не ниже девяти» — порог снова станет декоративным.
- **Формулировками двигаются не все оси.** После v8 `safety`, `realism` и `personalization`
  стоят на 2 во всех замеренных прогонах; ужесточение текста поменяло только `specificity`
  и `clarity`. Хочешь сдвинуть число раундов — крути `APPROVE_SCORE`, а не эпитеты
  в рубрике. Проверять это можно только замером на настоящих прогонах.
- **`APPROVE_SCORE = 9` держит калибровку на грани.** Простая задача берёт 10 и проходит
  за раунд, серьёзная получает revise, а средняя ложится ровно на 9 и будет прыгать между
  одним и двумя раундами от прогона к прогону. Это выбранная точка, а не случайность:
  десятка потребовала бы идеала и гоняла бы цикл до потолка.
- **Многораундовые прогоны чаще ловят баг DeepSeek с `reasoning_content`** (см. запись
  ниже): ходов вдвое больше — шансов упасть вдвое больше. Решение оставить модель как есть
  принято осознанно, и цена ему — часть серьёзных задач падает пятисоткой вместо второго
  раунда.
- **У коуча с v8 есть раздел «Когда остановиться», и он стоит перед «Списком покупок».**
  Список обязан остаться последним: `sourceText` в `shopping.ts` ищет его по заголовку,
  а запасной разбор шарит по всему плану. Появятся в стоп-сигналах граммы — запасной путь
  утащит их в корзину.

- **`deepseek-v4-flash` — модель с режимом размышления, и цикл тулов из-за этого падает
  недетерминированно.** Когда модель на каком-то ходу решила подумать, DeepSeek требует
  вернуть `reasoning_content` во **всех** последующих ходах диалога, а `@openai/agents`
  этого поля не знает вовсе (ноль вхождений в пакете). Итог — `400 The reasoning_content
  in the thinking mode must be passed back to the API` на середине прогона. Стрим тут
  ни при чём: щуп из четырёх тулов роняет одинаково и `run(...)`, и `run(..., {stream:true})`
  на одном и том же втором ходу. Прогон из 5 тулов проходит, из 16 проходит, из 11
  падает — зависит от того, включилось ли размышление, а не от их числа. Лечится
  `modelSettings: { providerData: { thinking: { type: 'disabled' } } }` у агентов
  (проверено: тот же щуп проходит все 5 ходов), но это меняет поведение модели во всех
  прогонах и в evals, поэтому решение принимать осознанно.
- **`AgentEvent` — контракт трёх слоёв.** Харнесс шлёт, `createStepWriter` в роуте
  переводит в `data-step`, `chat.tsx` рисует. Добавил вариант в union — правь оба
  остальных места, иначе шаг молча не появится в таймлайне: `switch` в роуте разберёт
  только известное ему.
- **Мест, знающих внутренности SDK, ровно два:** `toolCalls.ts` (не-стрим, разбор
  `newItems` после захода) и `streamCoach.ts` (стрим, разбор `RunStreamEvent`).
  Ответственность одна, форм две, потому что двумя способами их отдаёт SDK. Третьего
  быть не должно.
- **`emitter.active` решает, стримить ли заход коуча, и читает его только `streamCoach`.**
  Не-стрим ветка обязана остаться обычным `run(...)`: по ней идут evals, replay
  и `/api/agent/run`. Сделаешь стрим безусловным — evals пойдут по непроверенному пути.
- **`review-done` шлётся после `enforceApproveThreshold`, а не до.** Иначе в таймлайне
  встанет `approve`, который прогон не признал, гейт не открыл и на диск ничего не записал.
- **Дельты коуча — черновик, а не план.** В сообщение чата план стримится после цикла
  из `result.plan`: наружу уезжает `finalRound`, и он не обязан быть последним раундом.
  Начнёшь писать дельты прямо в текстовую часть — рано или поздно покажешь человеку план,
  который прогон отбросил.
- **Фильтр дельт — по `data.type === 'output_text_delta'`.** Рядом идут сырые
  провайдерские события `type: 'model'`, их втрое больше; проверка «есть строковое поле
  delta» утащила бы в план их содержимое.
- **`id` шага несёт префикс прогона** (`stepIds(run)` в `chat-protocol.ts`). Сессия копит
  прогоны в одной ленте, и без префикса третий прогон рискует затереть вердикт первого
  реконсиляцией data-частей.
- **Шаг пишется целиком, а не патчем.** Запись data-части с тем же `id` заменяет данные,
  а не сливает; поэтому `createStepWriter` держит карту состояний. Отправишь «только
  статус» — сотрёшь `phase` у плана и `tool` у вызова.
- **Кнопка «в notion» — только на последнем одобренном плане.** `/api/plan/notion` сверяет
  текст с `data/output.md`, где лежит план последнего одобренного прогона; на старом
  сообщении сессии она гарантированно даст `409`.
- **Превью черновика троттлится и сбрасывается принудительно на `review-start`.** Снимешь
  троттлинг — роут пошлёт сотни килобайт на план в три килобайта. Уберёшь принудительный
  сброс — потеряются последние строки плана, те самые, которые человек и ждёт.
- **`chat-protocol.ts` обязан оставаться типами и константами.** Он импортируется
  клиентским компонентом; любая исполняемая строка оттуда уедет в браузерный бандл вместе
  с тем, что она тянет.
- **Границы раундов объявлены дважды** — `DEFAULT_MIN_ROUNDS` и `DEFAULT_MAX_ROUNDS` в
  `runHealthAgent.ts` (это дефолты параметров `minRounds` и `maxRounds`) и `MIN_ROUNDS`
  с `MAX_ROUNDS` в `chat.tsx` (там они стоят в подписи вердикта).
  Тянуть значения из харнесса в клиент нельзя — это серверный модуль. Меняешь одно —
  меняй парное.
- **`MODEL` тоже продублирована** во всех трёх файлах `src/agents/` и четвёртый раз в `traceRun.ts`
  (там она едет в трейс). Отдельного модуля конфигурации намеренно нет. В `traceRun` она
  читается **внутри функции**, а не на уровне модуля: скрипты грузят `.env` первым импортом,
  а тела импортированных модулей выполняются раньше — константа успела бы взять дефолт.
- **`API-post-page` названо в консоли не подписью, а условием.** Кроме `TOOL_LABELS` это имя
  стоит в `NOTION_CREATE_PAGE` в `chat.tsx`, и по нему решается, показывать ли кнопку
  «в Notion». Разъедется с `NOTION_TOOLS.createPage` — кнопка молча перестанет появляться
  (или появится там, где агент уже всё сохранил). Ни сборка, ни прогон этого не заметят.
- **Вид инструмента считает `kindOf` в `chat.tsx`** — и в трейсе, и в живом таймлайне,
  по имени (`searchKnowledge` → rag) и по источнику (есть → mcp, нет → навык). Порядок
  проверок важен: RAG-тул локальный, источника у него нет, и без первой ветки он был бы
  неотличим от навыка в коде. Вид кодируется иконкой и словом, **но не цветом** — цвет
  в интерфейсе говорит только о вердикте ревьюера.
- **Источник тула едет в самом событии `tool`, а не берётся из `toolSources`.** Карта
  `toolSources` приезжает наружу только внутри `HealthAgentResult`, то есть после цикла;
  живой таймлайн видит вызов сразу и до конца прогона карты не имеет. Пока источник брали
  оттуда, **каждый MCP-тул в живом таймлайне показывался навыком** и переставал врать
  только после того, как прогон заканчивался. Поэтому `streamCoach` получает `toolSources`
  параметром и кладёт `source` прямо в событие; в трейсе источник по-прежнему из карты —
  там она уже есть. Уберёшь параметр — ошибка вернётся молча: типы сойдутся, сборка
  пройдёт, а половина таймлайна будет называть чужие процессы своим кодом.
- **У строки тула нет кружка состояния — у неё иконка вида.** Роут пишет шаг тула сразу
  со `status: 'done'` (см. `case 'tool'` в `createStepWriter`), «в процессе» такой строки
  не бывает, и полый кружок на ней не появлялся ни разу. Рейка поэтому отдана
  происхождению: `.step__kind` стоит ровно там, где у остальных шагов `.step__mark`.
  Начнёшь писать тул со `status: 'running'` — состояние станет невидимым.
- **Имена тулов объявлены дважды** — в `src/mcp/toolNames.ts`, `src/mcp/servers.config.ts`
  и `src/skills/`, а второй раз в `TOOL_LABELS` в `chat.tsx`, где к ним привязана
  русская расшифровка. Причина та же, что у границ раундов: консоль клиентская, тянуть
  в неё серверный модуль нельзя. Тул без строки в `TOOL_LABELS` покажется в трейсе как
  «неизвестный тул» — но источник `[weather]` у него будет верный: тот приезжает данными
  в `toolSources`, а не из таблицы в консоли.
- **Имена MCP-тулов держит `src/mcp/toolNames.ts`, и обходить его нельзя.** Их читают
  два процесса: сервер регистрирует тулы по этим именам, харнесс по ним фильтрует —
  что коуч увидит, а что нет. Впишешь строку мимо константы — гейт на `save_health_plan`
  молча перестанет держать, и не заметят этого ни сборка, ни прогон: несовпавшее имя
  просто не попадёт под фильтр, и тул окажется доступен весь цикл. По той же причине
  `buildFinalizeInput` подставляет имя из `MCP_TOOLS`, а не пишет строкой.
  Импортировать имена **из `markdownHealthServer.ts` нельзя**: тело того модуля поднимает
  stdio-транспорт, и харнесс запустил бы сервер прямо в своём процессе.
- **Формат плана разбирается дважды, и парсеры не связаны.** `app/plan-markdown.tsx` делает
  из плана JSX, `src/mcp/markdownBlocks.ts` — блоки Notion. Оба урезаны под одну и ту же
  известную форму, которую задаёт промпт коуча (`# `, `## `, списки с вложенностью на один
  уровень, `**выделение**`). Меняешь форму в промпте — чини оба; сломается второй молча,
  потому что смотрят обычно на первый. У блоков есть свои пределы API Notion: 2000 символов
  на отрезок текста и 100 блоков на страницу, оба соблюдаются в конвертере.
- **Страница-родитель в Notion ищется по названию, точным совпадением.** `PARENT_PAGE`
  в `notionPage.ts` — это `Wellness`, и поиск отдаёт только то, что расшарено интеграции.
  Пустой результат почти всегда значит забытый шаг «на странице ⋯ → Connections», а не
  опечатку. Совпадение точное намеренно: поиск в Notion нечёткий и на «Wellness» охотно
  отдаёт «Wellness archive» — положить план не в ту страницу хуже, чем не положить.
- **Имена тулов в `servers.config.ts` — строки, и проверить их нечем.** У своего сервера
  они хотя бы сверяются глазами с `MCP_TOOLS`, а у чужих взяты из их выдачи. Опечатка
  в `tools` тихо отнимет у коуча тул, опечатка в `writeTools` — тихо снимет с него гейт
  (тул уедет в общий список и будет доступен весь цикл). Ни сборка, ни прогон этого
  не заметят. Единственная проверка — `npm run mcp:inspect`: там у каждого тула
  напечатано «коучу: да / нет / после approve», и расхождение видно сразу.
- **Обновил версию внешнего пакета — перечитай его список тулов.** Версии в `args`
  прибиты намеренно: сервер, переименовавший тул в минорной версии, молча оставит коуча
  без него.
- **Имя тула в промпте коуча — тоже связь.** `healthCoach.v8` перечисляет тулы поимённо,
  и `read_profile` там должен совпадать с `MCP_TOOLS.readProfile`, `openmeteo_get_forecast`
  и `write_file` — с тем, что стоит в `servers.config.ts`, а `searchKnowledge` — с
  `SEARCH_KNOWLEDGE` в `src/rag/searchKnowledgeTool.ts`. Расходится — коуч зовёт
  несуществующее и работает вслепую, без профиля или без прогноза, а прогон не падает.
- **Весь SQL живёт в `docs/`, нумерованными файлами, и номер — это порядок выполнения.**
  Отдельной папки миграций у проекта нет; `docs/001_*` создаёт таблицу, `docs/002_*`
  ставит векторный индекс. Новый шаг схемы — новый файл со следующим номером, а не
  правка старого: выполненный файл уже отработал в чужой базе, и переписывать его
  значит терять историю.
- **Размерность вектора названа трижды**: `vector(1536)` в `docs/001_*`, `EMBEDDING_MODEL`
  в `.env` и `EXPECTED_DIMENSIONS` в `scripts/ingest.ts`. Сменил модель — пересоздавай
  таблицу и переингесть целиком: сравнивать векторы разных моделей нельзя, и если
  размерность случайно совпала, поиск станет мусорным **молча**. Сверка в ингесте
  существует ровно ради того, чтобы этого не случилось незаметно.
- **Имя `searchKnowledge` объявлено четыре раза**: `SEARCH_KNOWLEDGE` в
  `src/rag/searchKnowledgeTool.ts`, `TOOL_LABELS` и `SEARCH_KNOWLEDGE` в
  `chat.tsx` (там оно не подпись, а условие — по нему строка подменяется
  на «⌕ knowledge: …» с иконкой `IconSearch`), промпт коуча и кейс
  `knowledge-based-recipe.json`. Причина
  дублирования та же, что у остальных: консоль клиентская, серверный модуль в неё
  не тянут.
- **`## ` — граница chunk.** Уйдёшь в `knowledge/*.md` на `###` или на `# ` — ингест
  соберёт файл в один гигантский chunk или в ноль. Ни сборка, ни прогон этого не заметят:
  видно только по числу секций в логе `npm run ingest`, поэтому его и печатают по файлам.
- **Первый абзац секции обязан быть сводкой.** В вектор идут только заголовок и он;
  остальное тело хранится и отдаётся коучу, но не ищется. Начнёшь секцию с вступления
  вместо сути — она перестанет находиться, и это не сломает ни сборку, ни прогон:
  просто в выдаче будет что-то другое. Это цена за то, что рецепты вообще находятся
  (см. раздел про `embeddableText` выше).
- **`ivfflat` на Supabase не собирается с настройками по умолчанию.** Сборка берёт
  выборку около 10 000 векторов независимо от размера таблицы — это ~59 МБ при
  `maintenance_work_mem` в 32 МБ, и `create index` падает. В `docs/002_*` поэтому стоит
  `set maintenance_work_mem = '128MB'` в том же файле: `SET` живёт сессию, и выполнять
  его надо вместе с `create index`, одним запуском.
- **`retrievals` и `toolCalls` сшиваются по порядку.** Консоль считает, что n-й вызов
  `searchKnowledge` — это n-я запись журнала. Начнёт тул писать в журнал не на каждый
  вызов (например, «не логировать пустую выдачу») — нумерация поедет, и запрос встанет
  напротив чужого вызова. Поэтому запись делается и при ошибке базы.
- **`ivfflat` на пустой таблице бесполезен навсегда.** Он строится по данным, а
  `if not exists` при повторном запуске молча пропустит пересоздание. Отсюда и деление
  на два файла: `docs/001_*` → `npm run ingest` → `docs/002_*`. При росте базы до тысяч
  секций `lists = 4` надо поднимать примерно до корня из числа строк и перестраивать
  индекс. Оператор в `002` (`vector_cosine_ops`) обязан совпадать с тем, которым
  сортирует `matchChunks` (`<=>`), иначе индекс просто не будет использоваться.
- **`npm run ingest` затирает таблицу целиком.** Это и есть требуемая идемпотентность,
  но источник истины — `knowledge/`, и правки, сделанные в базе руками, он не сохранит.
- **Наш MCP-сервер запускается через `tsx`, и путь до него зашит** в `servers.config.ts` —
  `node_modules/tsx/dist/cli.mjs`. `tsx` лежит в `devDependencies`: прод-сборка без
  dev-зависимостей прогон не переживёт. Для учебного проекта это осознанно, но
  `npm ci --omit=dev` здесь сломает всё, кроме триаж-блокировки. Внешние серверы едут
  через `npx -y` с прибитой версией — их эта проблема не касается, зато касается сеть.
- **Внешним серверам нужен `clientSessionTimeoutSeconds`.** Дефолт SDK — 5 секунд, а `npx`
  на первом запуске качает пакет и не укладывается: прогон падал бы на таймауте при
  полностью исправном сервере. Константа `SESSION_TIMEOUT_SECONDS` в `connectServers.ts`,
  и такая же цифра продублирована в `scripts/mcp-inspect.ts`.
- **`enabled: false` и `requiresEnv` — разные вещи.** Сервер без `requiresEnv` живёт
  по `enabled`. Сервер с `requiresEnv` живёт по наличию переменной, и `enabled: false`
  его не удержит: так `notion` включается сам, когда в `.env` появляется `NOTION_TOKEN`.
  Значение переменной уезжает дочернему процессу — транспорт передаёт ему только
  `HOME/PATH/SHELL/TERM/USER`, и `.env` родителя ему не виден.
- **У списка покупок два источника, и это не дублирование.** `sourceText` в `shopping.ts`
  сперва ищет в плане раздел `## Список покупок` — его требует промпт коуча, когда список
  просили, и там продукты уже сведены и стоят по одному в строке. Нашёлся — разбирается
  только он, иначе те же граммы посчитались бы дважды: и в блюдах, и в списке. Не нашёлся —
  запасной путь по всему плану. **Промпт и парсер связаны:** переименуешь раздел в промпте —
  чини `SHOPPING_HEADING`, иначе разбор молча свалится на запасной путь.
- **Запасной разбор — эвристика под известный формат**, как и парсер плана. `nameBefore`
  берёт максимум два слова перед количеством и отсекает четыре класса мусора, каждый пойман
  на живом прогоне: пояснения в скобках («(150 г на омлет)» давало продукт «омлет»), маркеры
  списка («- рис»), инвентарь («2×12 кг» и слова из `NOT_BOUGHT`) и глаголы готовки («полить
  соком лимона»). Падежи не приводятся, и два разных продукта с общим первым словом
  склеиваются («филе лосося» + «филе трески» → «филе»). Это осознанный предел: морфологии
  здесь нет и не будет — потому раздел от коуча и предпочтителен.
- **Файл промпта обязан существовать.** `loadPrompt` бросает, если для версии из
  `ACTIVE_PROMPTS` нет файла в `prompts/`; на роуте это `500`, а не молчаливый прогон
  с пустым промптом. Имя файла собирается из `PROMPT_FILES`, переименовал агента —
  правь там.
- **Даты в `data/log.md` и подписи дней обязаны сходиться.** Содержание записей завязано
  на день недели: 8–9 августа это выходные (подъём в 10:00, «свободный день»), 11-е —
  вторник с переработкой, как обещает профиль. Правишь даты — пересчитывай подписи, и
  наоборот. Разъехавшись, они дают коучу второй, противоречащий календарю источник дат.
- **Промпт обязан описывать свой вход честно.** Ревьюер получает календарь, профиль,
  дневник, задачу и план; коуч — календарь и задачу; триаж — только задачу. Напишешь в промпте, что чего-то из этого нет, — модель
  послушается, и отвалится ровно та проверка, которая на этом входе держалась. Так v5
  ревьюера («исходную задачу ты не получаешь») перестал ставить `needs_human_professional`
  и одобрил запрос про дозировки при болях в груди.
- **Промпты несущие.** Промпт ревьюера задаёт ровно ту JSON-форму, которую разбирает
  `ReviewSchema` — включая `breakdown` из пяти именованных осей, — и список вердиктов
  в нём должен совпадать с enum. **Числового порога в промпте ревьюера с v8 нет вовсе** —
  он назван один раз, в `APPROVE_SCORE`. Это не упрощение, а исправление: пока промпт
  сообщал модели планку, она подгоняла под неё оси, и за 39 прогонов сумма ни разу
  не опустилась ниже порога — понижение `enforceApproveThreshold` не сработало ни разу.
  Вернёшь число в промпт — порог снова станет декоративным. Промпт триажа задаёт форму
  ответа, которую разбирает `parseTriage`: первое слово `WELLNESS` или `HUMAN`. Промпт коуча задаёт
  markdown-форму, которую разбирает [app/plan-markdown.tsx](app/plan-markdown.tsx) —
  это намеренно урезанный парсер под известный формат, а не универсальный. Классы
  `paper__*` он проставляет сам, так что переименование в CSS — это правка и в нём.
- **Фон продублирован в `layout.tsx`.** `viewport.themeColor` повторяет hex `--ink`
  (`#e7ebf3` светлый, `#070a12` тёмный) для светлой и тёмной темы; меняешь токен —
  меняй и там, иначе поедет цвет строки браузера на мобильном.
- **`score` считается ровно по пяти осям, по 2 балла за ось.** Оси перечислены в
  `BreakdownSchema` и в `safetyReviewer.v8`, и эти два списка обязаны совпадать по именам:
  разъедутся — Zod не примет ответ и прогон упадёт после ретрая. Блокирующие проверки
  («задача выполнена», «профиль соблюдён буквально») стоят **до** осей и баллов не дают —
  иначе осей стало бы семь и шкала 0–10 поехала бы вместе с десятью делениями в разметке.
  Отсюда законный и ожидаемый исход: `revise` при `score` 10, когда план хорош, но отвечает
  не на то, о чём просили. Добавляешь ревьюеру новое требование — решай, оно ось
  (тогда пересчитывай шкалу везде) или блокирующая проверка (тогда без баллов).
- **Шкала оценки — ровно 10 делений**, потому что ревьюер ставит 0–10, а шкала раундов
  рисуется по `MAX_ROUNDS`, где первые `MIN_ROUNDS` делений полные, а остальные короче
  (`.rounds__slot--spare`) — обязательные раунды против запаса. Меняется диапазон в
  схеме — меняется и разметка.
- **Оценка показывается только там, где есть план.** Это правило действует и в шкале
  ворот, и в трейсе: при `needs_human_professional` вместо числа прочерк, иначе
  интерфейс оценивает то, чего нет.
- **Блок `prefers-reduced-motion` в конце globals.css** гасит всю анимацию поимённо.
  Добавил новую — допиши её туда же. Гасятся не только `@keyframes`, но и наведения,
  которые двигают элемент (`transform` у `.preset`, `.copy`, `.composer__send`,
  `.chat__down`): у `.chat__down` при этом надо вернуть `translateX(-50%)`, иначе
  кнопка уедет от центра — она этим же свойством и центрируется.
- **Стекло объявлено одним общим селектором** в разделе «Материал» globals.css. Новая
  панель — это дописать её в тот список, а не скопировать четыре строки с
  `backdrop-filter` по месту: разъехавшись, копии дадут панели, которые выглядят
  почти одинаково, и разницу никто не заметит, пока не сменится тема.
- **`.copy` — общий класс трёх разных кнопок**: «новый чат» в шапке, «скопировать»
  и «в notion» под планом. Селектор общий для `button` и `a` намеренно: «открыть
  в notion» — ссылка, а выглядеть обязана как соседняя кнопка. Правишь `.copy` —
  смотри на все три места.
- **Пути к данным только через `process.cwd()`.** После сборки харнесс лежит внутри
  `.next/`, и `import.meta.url` укажет не туда.
- **`serverExternalPackages: ['@openai/agents', 'pg']`** в `next.config.ts` нужен, чтобы
  оба грузились нативным `require`, а не через бандл. У `pg` это отложенный require
  необязательного `pg-native`: собранный бандлером драйвер падает на первом запросе,
  хотя `npm run build` проходит зелёным.
- **Модуль может только отнимать тул.** Ветка `writeTools` в `buildToolFilter` стоит
  первой намеренно: поменяешь порядок — модуль, забывший `save_health_plan`, молча
  перестанет сохранять план, и не поймает этого ни сборка, ни `mcp:inspect`. Порядок
  проверок в `access` у `scripts/mcp-inspect.ts` обязан повторять `buildToolFilter`,
  иначе скрипт начнёт врать ровно про то, ради чего его смотрят.
- **Имена тулов в модулях — константы.** Строка мимо `MCP_TOOLS` / `LOCAL_TOOLS` /
  `WEATHER_TOOLS` / `SEARCH_KNOWLEDGE` тихо отнимет у модуля тул. Единственная проверка —
  `npm run mcp:inspect -- --module <имя>`.
- **Порога роутера в `prompts/router.v1.md` нет.** Вернёшь число в текст — модель начнёт
  подгонять `confidence` под него, ровно как ревьюер подгонял `score` до v8.
- **Осечка роутера обязана давать `general`.** Бросать при непонятном ответе нельзя:
  за роутером стоит рабочее поведение по умолчанию, а за падением не стоит ничего.
- **`AgentEvent` — контракт трёх слоёв, и вариант `module` не исключение.** Правится
  в `events.ts`, в `createStepWriter` и в `chat.tsx` одновременно.
- **Наслойка модуля не повторяет формат плана.** Впишешь в `prompts/modules/*.md` свою
  структуру разделов — молча сломаешь `plan-markdown.tsx`, `markdownBlocks.ts` или разбор
  списка покупок.
- **`description` модуля — вход роутера, а не комментарий.** Правишь описание — меняешь
  маршрутизацию, и заметят это `evals`, а не человек.
- **`check_habit` пишет без гейта** — единственное явное исключение в проекте. Завёрнутый
  ревьюером прогон всё равно оставит след в `data/habits.md`.
- **Дневниковая запись помечена `### Предложено агентом`.** Уберёшь пометку или её
  описание из `safetyReviewer.v9` — ревьюер начнёт считать намерения фактами и одобрит
  план, который «уже сработал», хотя не сработало ничего.
- **`ROUTER_MODEL` читается внутри функции.** На уровне модуля константа рискует взять
  дефолт: скрипты грузят `.env` телом первого импорта. Та же причина, что у `traceRun`.
- **`MODULE_LABELS` и `GENERAL_MODULE` продублированы в `chat.tsx`.** Причина та же, что

  Модуль без строки покажется машинным именем; `GENERAL_MODULE`, разъехавшись

- **`AGENTS.md` в корне перезаписывает сам `next dev`** — свои правила туда не дописывать.

## Стиль

Комментарии, тексты интерфейса и промпты — на русском. Комментарии объясняют причину
решения, а не пересказывают код; такой плотности и стоит держаться.

Весь вид собран в одном файле — [app/globals.css](app/globals.css), обычный CSS с
токенами и семантическими классами. Ни Tailwind, ни CSS-модулей, ни `style`-пропсов.
Новый блок интерфейса — это новый класс в globals.css, а не утилиты в разметке.
В проекте лежит скилл [.agents/skills/frontend-design](.agents/skills/frontend-design) —
при работе над UI имеет смысл его прочитать.

### Материал — стекло

Панели интерфейса полупрозрачны и размывают то, что под ними: `--glass` / `--glass-2`
(заливка), `--glass-line` (волосяная кромка), `--glass-rim` (блик по верхней грани,
он же `inset 0 1px 0` в тени), `--glass-blur` / `--glass-blur-lg` и `--glass-sat`.
**Объявлено это ровно один раз** — общим селектором в разделе «Материал», куда вписаны
все стеклянные поверхности разом. Радиус там не задаётся: он про роль панели, а не про
материал, и стоит по месту из шкалы `--r-xs … --r-pill`.

Стеклу нужно что-то размывать, иначе оно неотличимо от матовой панели. Поэтому
за содержимым лежит `body::before` — фиксированный слой со световыми пятнами
(`--ground`), который очень медленно дрейфует (`@keyframes drift`, 44 секунды в одну
сторону). Слой именно фиксированный и именно псевдоэлемент: свет не должен ехать
вместе с лентой, а разметке о нём знать незачем.

**Без `backdrop-filter` стекло становится матовым.** Блок `@supports not` поднимает
`--glass` почти до непрозрачного: полупрозрачная панель без размытия — это текст
поверх текста, а не материал.

Плавающие над лентой поверхности (`.topbar__mark`, `.topbar .copy`, `.composer`,
`.chat__down`) размыты сильнее и залиты плотнее остальных: под ними проезжает текст.
Лента при этом обрезана маской по краям (`mask-image` у `.chat__log`) — иначе видно,
что панели не висят над текстом, а обрываются вместе с ним.

**Планки во всю ширину над лентой нет.** Сверху две отдельные капсулы — знак слева,
«новый чат» справа; сам `.topbar` прозрачен и служит только раскладкой (отсюда
`pointer-events: none` на нём и `auto` на детях, иначе невидимая планка перехватывала бы
клики по ленте). Контекста, счётчика прогонов и рассказа про раунды там нет намеренно:
прогон рассказывает о себе сам, как только начинается, и повторять это надписями над
пустым экраном значит занимать место под то, что появится через секунду. По той же
причине пустой экран — это знак, вопрос в два слова и четыре заготовки, а вертикально
он центрируется через `.chat__log:has(.empty)`: лента прогонов растёт сверху вниз,
а пустому экрану расти неоткуда.

### Две поверхности: чернила и бумага

Страница — «чернила» (`--ink`, `--panel`, `--chalk`, `--dim`). План — «бумага»
(`--paper*`): тёплый светлый лист внутри страницы. Палитры независимы, и **бумага
остаётся светлой даже в тёмной теме** — план читается как распечатка, вынутая из
интерфейса, а не как ещё одна панель. Тёмная тема только через `prefers-color-scheme`,
переключателя нет и он не нужен.

### Цвет говорит только о вердикте

Страница монохромная; jade / amber / coral появляются исключительно там, где высказался
ревьюер: `.verdict`, `.step__verdict` и `.specialist`. Тон задаётся один раз классом
`is-jade|is-amber|is-coral` и протягивается вниз через переменную `--sig`. Решает тон
`chat.tsx` (таблица `TONES`), CSS только исполняет. Поэтому новый вердикт — это правка
в трёх местах: enum схемы, `TONES` в консоли и тройка селекторов `.verdict.is-*`.

**Происхождение инструмента цветом не кодируется.** Метки `mcp / rag / навык` различаются
иконкой и словом, а состояние шага таймлайна — полым и залитым кружком (`.step__mark`).
Раскрасить их значило бы отнять у цвета его единственное значение.

Иконки живут в `chat.tsx` (`IconPlug`, `IconSparkle`, `IconBraces`), а не в CSS: это
разметка. Силуэты выбраны так, чтобы различаться с одного взгляда при 14 px — **вилка**
(чужой процесс, подключён снаружи), **искра** (нашлось по смыслу), **фигурные скобки**
(функция здесь, в коде). Прежние залитый квадрат, залитый круг и пустой квадрат при 7 px
почти не различались и стояли вторым примитивом рядом с кружком состояния — две похожие
точки подряд в начале каждой строки.

Вид и источник собраны в одну капсулу `.kind`, а не идут тремя кусочками текста подряд:
россыпью они читались как продолжение строки, а не как подпись к ней. В таймлайне капсула
идёт без иконки — та же иконка стоит в рейке слева; в трейсе иконка внутри капсулы,
потому что рейку там занимает номер вызова.

**Исключение ровно одно и оно холодное:** знак пустого экрана `.empty__orb`, точка
`.topbar__dot` и световой фон `--ground` держатся гаммы «синий → циан → фиалка».
Смысла они не несут — это материал, а не сигнал, — и спутать их с jade / amber / coral
нельзя по построению: ни один из трёх сигнальных тонов в эту гамму не попадает.
Добавишь туда зелёный, янтарный или красный — правило про вердикт перестанет работать.

### Ход работы → план → вердикт

Ассистентское сообщение — это запись прогона сверху вниз: таймлайн этапов, «бумага»
с планом, карточка вердикта, свёрнутый трейс. Порядок не случаен: пока прогон идёт,
единственное содержимое сообщения — таймлайн, и он обязан стоять первым; когда прогон
кончился, ответ — это план, и вердикт читается после него, а не вместо.

**Живой таймлайн развёрнут, отработавший сворачивается** (`.timeline__live` против
`.timeline__past`). Сессия копит прогоны в одной ленте, и пять развёрнутых таймлайнов
подряд хоронят под собой то, ради чего всё затевалось.

При `needs_human_professional` вместо плана стоит `.specialist`, и плана нет вовсе —
то же защитное правило, что и в харнессе (`plan: null`, `redactPlans`), только показанное.

### Две гарнитуры на две роли

`layout.tsx` подключает через `next/font/google` Onest (`--font-body` — весь текст,
от слова вердикта до подписи) и JetBrains Mono (`--font-mono` — машинные данные,
утилита `.mono`). У обеих обязателен `subsets: ['cyrillic', 'latin']`: интерфейс
русский, и гарнитура без кириллицы ломает страницу молча.

**Отдельной вывесочной гарнитуры нет намеренно.** Иерархию задают кегль, вес
и отрицательная разрядка — так это устроено в системной эстетике Apple, на которую
интерфейс опирается, и третий шрифт там только мешал бы. Прежний Unbounded (широкий,
характерный) спорил с этим сильнее всего и потому убран; `--font-display` больше
не существует, и ссылок на него в CSS быть не должно.

Первым в стеке `body` стоит `-apple-system`: на macOS и iOS страница набрана SF,
на остальных — Onest, тот же нейтральный гротеск. Метрики у них близкие, поэтому
вёрстка от подмены не едет.

## При работе с БД и миграциями
- всегда создавай `.sql` файлы для любых SQL-запросов, которые пользователь должен выполнить
- помещай все `.sql` файлы в папку `/docs` в соответствующем проекте
- каждый файл должен начинаться с номера, чтобы фиксировать порядок выполнения операций
- вся схема базы данных должна быть задокументирована в папке `/docs` в отдельных `.sql` файлах
- называй файлы в таком формате: `001_create_x_table.sql`, `002_change_rls_policy.sql`, `003_add_foreign_key.sql` и т.д.
