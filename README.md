# Wellness-агент

Триаж отсеивает задачи для живого специалиста, коуч пишет план, ревьюер проверяет его
на безопасность. Оркестрация живёт в коде: сколько будет раундов и что делать
с вердиктом, решает цикл, а не текст промптов.

## Запуск

```bash
npm install
npm run dev          # http://localhost:3000
```

Нужен `.env` в корне:

```
DEEPSEEK_API_KEY=...
DEEPSEEK_MODEL=deepseek-v4-flash

# база знаний: эмбеддинги и Postgres с pgvector
OPENAI_API_KEY=sk-...
EMBEDDING_MODEL=text-embedding-3-small
SUPABASE_DB_URL=postgresql://postgres.<ref>:<пароль>@aws-0-<регион>.pooler.supabase.com:6543/postgres

# необязательно: появится токен — сам поднимется Notion-сервер, не появится — не поднимется
NOTION_TOKEN=ntn_...
```

Ключей два, и это не опечатка: модель живёт на DeepSeek, а эндпоинта эмбеддингов
у DeepSeek нет вовсе — поэтому база знаний считается отдельным провайдером. Строку
подключения берут в Supabase → Connect → Transaction pooler: прямое подключение там
только по IPv6 и работает не везде.

Внешние MCP-серверы (погода, файлы, Notion) ставить отдельно не нужно: они едут через
`npx` при первом прогоне. Первый запуск из-за этого дольше на несколько секунд.

Что увидит агент — без похода в модель, дёшево и после любой правки в `src/mcp/`
или `src/os/modules/`:

```bash
npm run mcp:inspect                       # тулы и ресурсы всех серверов
npm run mcp:inspect -- --module recipes   # что из тулов отнимает модуль OS
```

### База знаний: миграция и ингест

Схема лежит в `docs/` пронумерованными `.sql`-файлами — номер и есть порядок выполнения:

```bash
# 1. выполнить docs/001_create_knowledge_chunks_table.sql в SQL Editor
# 2. посчитать эмбеддинги и залить knowledge/*.md в таблицу
npm run ingest
# 3. docs/002_create_knowledge_embedding_index.sql — необязателен, см. ниже
```

Порядок важен, и `002` стоит после ингеста не случайно: `ivfflat` делит пространство
векторов на кластеры по существующим строкам, и построенный на пустой таблице он
останется бесполезным навсегда — `if not exists` это лишь закрепит.

**На нынешнем размере базы шаг 3 можно пропустить.** 67 секций перебираются полностью
за миллисекунды, а приближённый индекс с `lists = 4` смотрит только один кластер
из четырёх и может не увидеть настоящий топ-5. Файл лежит на вырост; когда база
дорастёт до тысяч секций, он понадобится. Если создаёте его сейчас — выполняйте файл
целиком: там есть `set maintenance_work_mem`, без которого Supabase отказывает
(«memory required is 59 MB»), потому что сборка `ivfflat` берёт выборку фиксированного
размера независимо от числа строк.

`npm run ingest` идемпотентен и разрушителен одновременно: он очищает таблицу и заливает
её заново. Повторный запуск дублей не создаёт, но и правки, сделанные в базе руками,
стирает — источник истины здесь `knowledge/`, а не Postgres. Без базы приложение работает:
тул вернёт «база знаний недоступна», и коуч допишет план по профилю и дневнику.

## Структура

```
app/page.tsx                     серверная страница: рейка с контекстом агентов
app/chat.tsx                     чат: таймлайн этапов, план, вердикт, сессия прогонов
app/chat-protocol.ts             контракт потока: Step, ResultData, stepIds
app/plan-markdown.tsx            разбор markdown, который отдаёт коуч
app/api/chat/route.ts            POST { messages } → SSE: шаги, план по кускам, итог
app/api/agent/run/route.ts       POST { task } → { plan, review, rounds } одним ответом
src/agents/healthCoach.ts        агент-коуч
src/agents/safetyReviewer.ts     агент-ревьюер
src/agents/safetyTriage.ts       агент-триаж: задача для коуча или для врача
prompts/                         тексты промптов по версиям, ACTIVE_PROMPTS выбирает
src/harness/runHealthAgent.ts    клиент DeepSeek, триаж, цикл на 3 раунда, жизнь MCP-серверов
src/harness/events.ts            AgentEvent и эмиттер: чем прогон отчитывается по ходу
src/harness/streamCoach.ts       заход коуча: стримом, когда за ним следят, иначе обычным run
src/harness/traceRun.ts          след прогона на диск, runs/run-*.json
src/mcp/servers.config.ts        реестр MCP-серверов: что поднимать и что из этого давать
src/mcp/connectServers.ts        поднимает всё включённое, строит карту «тул → сервер»
src/mcp/markdownHealthServer.ts  наш MCP-сервер над data/: 8 тулов, 6 ресурсов, stdio
src/mcp/toolNames.ts             имена тулов и URI ресурсов — объявлены один раз
src/skills/                      локальные тулы: шаблоны тренировок и список покупок
src/rag/                         база знаний: chunks, эмбеддинги, pgvector, тул поиска
knowledge/                       сама база знаний в markdown — источник истины для ингеста
docs/00N_*.sql                   схема БД: нумерованные шаги, номер = порядок выполнения
scripts/ingest.ts                knowledge/*.md → эмбеддинги → Postgres, очищая и заливая
scripts/replay.ts                переигрывает прогон из трейса и диффает с ним
scripts/eval.ts                  гоняет evals/cases/*.json, печатает PASS/FAIL
scripts/mcp-inspect.ts           печатает тулы и ресурсы всех серверов конфига
data/profile.md                  профиль человека (в том числе город — для погоды)
data/log.md                      дневник
data/recipes.md                  любимые рецепты — личное, не путать с knowledge/recipes.md
data/output.md                   сюда пишется одобренный план
plans/                           сюда агент кладёт копии планов через filesystem MCP
runs/                            трейсы прогонов (в .gitignore, кроме run-example.json)
```

Веб — единственный вход, и оба роута ведут в одну и ту же функцию: `runHealthAgent`.
Разница только в том, когда они говорят. `/api/chat` подписывается на события прогона
и стримит их по мере поступления — им ходит интерфейс. `/api/agent/run` ждёт конца
и отдаёт один JSON — им ходят `replay`, `eval` и curl из терминала.

## Путь проекта

Проект рос слоями, и каждый слой решал задачу, которую предыдущий решить не мог.
Девять абзацев — девять шагов от одного файла до операционной системы.

**agent.** Началось с одного `index.ts`: агент, промпт, вызов модели, `console.log`.
Этого хватало, чтобы увидеть главное — модель, у которой есть инструменты, ведёт себя
иначе, чем модель, которой задают вопрос. Не хватало всего остального: результат жил
в терминале, сравнить два прогона было нечем, а «хороший план» оставался вопросом вкуса.

**UI.** Появилась страница: задача в поле, план на экране. Не украшение — до неё агента
показывать было некому, а всё, что нельзя показать, тихо остаётся черновиком. Заодно
выяснилось, что прогон идёт от двадцати секунд до нескольких минут, и человек всё это
время смотрит в пустоту.

**harness.** Оркестрация переехала из промптов в код: цикл раундов, второй агент-ревьюер,
порог одобрения, гейт на запись. Это перелом всего проекта. Промпт — просьба, и модель
её иногда не выполняет; цикл в `runHealthAgent.ts` — гарантия, и обойти его нельзя.
Отсюда правило, которое дальше не нарушалось ни разу: **сколько будет раундов и что
делать с вердиктом, решает код, а не текст**.

**tools.** Коуч перестал выдумывать факты о человеке и начал их доставать: профиль,
дневник, рецепты, шаблоны тренировок, список покупок. Стало видно, что описание тула —
это часть промпта, а не комментарий: по нему модель решает, звать ли навык, и правка
описания меняет поведение так же, как правка инструкции.

**traces.** Каждый прогон стал оставлять `runs/run-*.json`, а поверх трейсов появились
`npm run replay` и `npm run eval`. До этого «стало лучше» было впечатлением; после —
таблицей PASS/FAIL. Ровно здесь проект перестал быть демонстрацией и стал системой,
которую можно менять, не ломая молча.

**MCP.** Доступ к данным человека уехал в отдельный процесс за стандартным протоколом,
а три чужих сервера — `filesystem`, `weather`, `notion` — подключились записью в конфиге,
без единой строки кода интеграции. Урок оказался не в протоколе, а в границе: **для
агента разницы между своим и чужим тулом нет**, а гейт на запись обязан распространяться
и на чужие серверы, иначе он декоративный.

**RAG.** Рядом с личной памятью появилась база знаний: `knowledge/*.md` в Postgres
векторами, поиск по смыслу. Здесь стало ясно, что памяти две и они не взаимозаменяемы.
Профиль читается **целиком и точно** — потому что вопрос «про кого план». База знаний
достаётся **приблизительно, топ-5** — потому что вопрос «из чего его собрать».
Перенести профиль в вектора нельзя: точное чтение там не заменяется похожестью.

**chat.** Прогон начал рассказывать о себе по ходу: `onEvent` в харнессе, таймлайн
в интерфейсе, план стримом. Главное следствие оказалось архитектурным — наружу уезжает
**последний одобренный** раунд, а не последний, поэтому дельты коуча это черновик,
и настоящий план стримится после цикла. Показать человеку план, который прогон отбросил,
хуже, чем показать его на секунду позже.

**OS.** Последний слой связал всё: роутер намерения одним дешёвым заходом выбирает модуль,
модуль подставляет промпт-наслойку и сужает список тулов, а после одобрения харнесс
дописывает след в память. Модулей восемь, агент по-прежнему **один** — модуль это
конфигурация, а не отдельный агент, и в этом весь смысл: восемь агентов означали бы
восемь дорог мимо ревьюера. Safety Reviewer остался обязательным для каждого модуля
и ни одним из них не параметризуется.

## Memory vs RAG

У коуча две памяти, и путать их — главная ошибка при чтении этого кода. `data/profile.md`
и `data/log.md` — это **личная память**: кто ты, какие у тебя цели, травмы,
непереносимости и что реально происходило на прошлой неделе; она достаётся целиком
и точно, тулами `read_profile` и `read_recent_logs`, потому что профиль надо прочитать
весь, а не «пять самых похожих кусков». `knowledge/` — это **база знаний**: что мы вообще
умеем предложить любому человеку, то есть рецепты, нормы белка, шаблоны недели и правила
восстановления; её достают тулом `searchKnowledge` по смыслу запроса, потому что читать
её целиком незачем и не влезет. Разница не в формате хранения, а в вопросе, на который
каждая отвечает: личная память отвечает «про кого план», база знаний — «из чего его
собрать». Отсюда и разные механизмы: личное лежит в markdown за MCP-сервером и меняется
каждый день, общее лежит в Postgres векторами и меняется раз в месяц. Поэтому
`data/recipes.md` (что человек правда готовит) и `knowledge/recipes.md` (что мы умеем
готовить) — не дубликаты, а два разных источника, и хороший план берёт из обоих:
привычное блюдо из первого, новое — из второго.

| | Личная память | База знаний |
|---|---|---|
| Отвечает на | кто ты | что мы умеем |
| Где | `data/*.md` | `knowledge/*.md` → Postgres |
| Как достаётся | целиком, точным чтением | топ-5 по смыслу запроса |
| Чем | `read_profile`, `read_recent_logs`, `list_recipes` (MCP) | `searchKnowledge` (локальный тул) |
| Как часто меняется | каждый день | редко, руками, через `npm run ingest` |

### Как устроен сам RAG

Один embed запроса, один similarity search — и всё:

```
searchKnowledge(query)
  → embed([query])                         один POST в /v1/embeddings
  → select … 1 - (embedding <=> $1) …      один запрос в Postgres, order by <=>
  → 5 chunks с file, heading, similarity
```

Ни reranking, ни hybrid search, ни переписывания запроса здесь нет намеренно: каждое
из них добавляет ещё один поход в модель и ещё одно место, где выдача меняется незаметно,
а показать нужно сам механизм. Chunk — это одна `##`-секция markdown целиком: границы
выбирал человек заголовками, а не счётчик символов, поэтому найденный кусок не обрывается
посреди состава блюда.

В вектор при этом уходит не весь chunk, а заголовок и первый абзац. Эмбеддинг усредняет
весь текст, и длинный хвост глушит заголовок: у рецепта хвост — список граммов, в котором
смысла почти нет. С полным телом запрос «ужин с высоким белком без молочки» не находил
ни одного рецепта ужина в топ-5; с первым абзацем находит все пять. Коучу при этом
отдаётся секция целиком — урезан только вектор, и поэтому первый абзац каждой секции
обязан быть сводкой, а не вступлением.

Что искал агент и что нашёл — видно в трейсе прогона (`runs/run-*.json`, поле
`retrievals`) и в консоли под заголовком «что сделал агент»:

```
что сделал агент      ◼ mcp — отдельный процесс  ● rag — база знаний  ◻ навык — функция в коде

1  ◼ mcp markdown-health  read_profile            прочитал профиль
2  ◻ навык                suggestWorkoutTemplate  взял шаблон тренировки
3  ● rag knowledge        searchKnowledge         искал в базе знаний
   │ 🔍 knowledge: ужин с высоким белком без молочки → 5 chunks
   │ 0.63  recipes.md  Лосось с киноа и огурцом — ужин с высоким белком, без молочки
   │ 0.60  recipes.md  Паста с креветками и помидорами — ужин за пятнадцать минут
   │ 0.60  recipes.md  Треска с чечевицей — ужин с высоким белком, без молочки
4  ◼ mcp weather          openmeteo_get_forecast  запросил прогноз погоды
```

Вид инструмента подписан словом и помечен формой: залитый квадрат — чужой процесс за
протоколом, залитый круг — внешняя база, пустой квадрат — функция в этом же коде.
Цветом это не кодируется намеренно: цвет в интерфейсе говорит только о вердикте
ревьюера. Без такой пометки `searchKnowledge` выглядел бы обычным локальным навыком,
и то, что он ходит по сети в Postgres, из трейса было бы не видно.

Сама строка тула при этом остаётся в общем ритме списка — короткая расшифровка, как
у всех; запрос и найденное висят под ней вторым планом. Иначе длинная фраза в колонке
расшифровки ломала бы колонки, а капс машинного шрифта делал бы её нечитаемой.

## До MCP / После MCP

Раньше каждый источник данных подключался руками и жил внутри приложения: написать
функцию над файлом, обернуть её в `tool()` из Agents SDK, вписать в массив тулов коуча.
Шесть источников — шесть таких обвязок, и все шесть намертво прибиты к нашему процессу.
Отдать те же данные второму агенту или чужому клиенту было нечем: интерфейса наружу
не существовало вовсе, был только массив в памяти.

Теперь данные отдаёт **стандартный сервер**. `src/mcp/markdownHealthServer.ts` объявляет
тулы и ресурсы по протоколу MCP и говорит по stdio — подключиться к нему может кто угодно,
от нашего коуча до MCP Inspector. Приложение перестало быть единственным способом
добраться до `data/`.

```
До:   coach ──tool()──► функция ──► data/*.md          всё в одном процессе

После: coach ──MCP/stdio──► markdownHealthServer ──► data/*.md
       coach ──tool()─────► shopping, workouts          процесс приложения
```

| | до | после |
|---|---|---|
| профиль, дневник, рецепты, сохранение плана | `tool()` в `src/skills/` | тулы MCP-сервера |
| шаблоны тренировок, список покупок | `tool()` в `src/skills/` | там же, без изменений |
| кто ещё может взять эти данные | никто | любой MCP-клиент |
| имена в трейсе | `getProfile`, `savePlan` | `read_profile`, `save_health_plan` |

**Локальными остались ровно те два навыка, где данных человека нет.** Шаблоны тренировок
зашиты в код, а список покупок — разбор текста, который коуч только что написал сам.
Заводить стандартный сервер стоит там, где есть чужой источник данных; ради чистой
функции — незачем. Контраст оставлен намеренно: в трейсе видно оба вида тулов рядом,
и видно, что **для агента разницы нет** — он зовёт их одинаково.

Границу держим строго: в MCP уехал только доступ к данным. Оценка, валидация ревью,
порог одобрения и порядок раундов остались в харнессе — сервер не знает про прогон
ничего, в том числе одобрен ли план.

### Посмотреть сервер

```bash
npm run mcp:inspect            # состав сервера: тулы и ресурсы
npm run mcp:inspect -- --read  # плюс содержимое каждого ресурса
```

Поднимает сервер тем же способом, что и харнесс, и печатает его тулы и ресурсы — то,
что увидел бы любой клиент. Тулы при этом не зовутся никогда: среди них есть
`save_health_plan`, `append_daily_log`, `check_habit` и `update_preferences`, а «посмотреть
сервер» не должно переписывать `data/`. Ресурсы читать безопасно, и `--read` показывает
начало каждого.

Тулов у сервера **восемь, а коуч в прогоне видит шесть**: `append_daily_log`
и `update_preferences` ему не дают никогда (дневник — источник фактов, на который
опирается ревьюер, проверяя план на выдумки; предпочтения пишет только харнесс, после
одобрения), а `save_health_plan` появляется только после него же. Разницу держит харнесс
по записи в `src/mcp/servers.config.ts`, не сервер — в выводе `mcp:inspect` она напечатана
строкой «коучу» у каждого тула.

Тот же сервер в официальном MCP Inspector:

```bash
npx @modelcontextprotocol/inspector node node_modules/tsx/dist/cli.mjs src/mcp/markdownHealthServer.ts
```

### Ресурсы агенту не достаются

`profile://me`, `logs://recent`, `recipes://all`, `plans://latest`, `habits://all`,
`preferences://all` — вторая половина протокола: не «сделай», а «вот данные по адресу».
Agents SDK превращает в тулы агента только `tools`; ресурс надо запросить явно, и коуч
этого не делает. Они здесь ради Inspector — показать сервер целиком. Профиль коучу
приезжает тулом `read_profile`, а не по адресу `profile://me`.

### Гейт на запись после переезда

Политика «писать на диск можно только после `approve`» осталась в коде харнесса, но
исполняется теперь двумя разными способами — потому что тулы живут в разных процессах:

- **локальный** `generateShoppingList` спрашивает гейт внутри себя и возвращает отказ;
- **MCP-шный** `save_health_plan` исполняется в чужом процессе, куда замыкание не дотянется,
  поэтому его просто **нет в списке тулов**, пока гейт закрыт (`toolFilter`).

Второе строже первого: позвать то, чего в списке нет, модель не может. Сервер при этом
про одобрение по-прежнему не знает — он бы записал, если бы его позвали.

## Внешние серверы: интеграция — это конфиг, а не код

Свой сервер мы написали. Следующие три — взяли готовыми из npm, и **кода интеграции
не написали ни строчки**. Всё подключение — запись в `src/mcp/servers.config.ts`:

```ts
{
  name: 'weather',
  command: 'npx',
  args: ['-y', '@cyanheads/open-meteo-mcp-server@0.3.4'],
  env: { MCP_TRANSPORT_TYPE: 'stdio', MCP_LOG_LEVEL: 'error' },
  enabled: true,
  tools: ['openmeteo_search_locations', 'openmeteo_get_forecast'],
}
```

Харнесс читает этот массив, поднимает всё включённое и отдаёт тулы коучу единым списком.
**Добавить сервер — дописать запись; правок в харнессе это не требует.** Обёрток над
чужими тулами нет и быть не должно: агент получает их как есть, с их именами и схемами,
и в трейсе `openmeteo_get_forecast` стоит рядом с `generateShoppingList`.

### Что подключено

| Сервер | Пакет | Что даёт | Авторизация |
|---|---|---|---|
| `markdown-health` | наш, `src/mcp/markdownHealthServer.ts` | профиль, дневник, рецепты, сохранение плана | нет, локальный процесс |
| `filesystem` | `@modelcontextprotocol/server-filesystem` | чтение и запись файлов в `data/` и `plans/` | нет, права ОС |
| `weather` | `@cyanheads/open-meteo-mcp-server` | геокодинг города и прогноз Open-Meteo | **нет ключа вовсе** |
| `notion` | `@notionhq/notion-mcp-server` | страница плана в Notion | `NOTION_TOKEN` в `.env` |

Про `weather`: Open-Meteo бесплатен и не требует регистрации для некоммерческого
использования, поэтому сервер поднимается без единого секрета. Из одиннадцати его тулов
коучу отдаются два — остальные про наводнения, морские волны и климатические проекции.
Это не обёртка, а длина списка: DeepSeek выбирает тул тем хуже, чем список длиннее.

Про `notion`: `enabled: false`, но `requiresEnv: 'NOTION_TOKEN'`. **Есть токен —
сервер поднимается сам; нет — молча пропускается, и прогон идёт как ни в чём не бывало.**
Токен — internal integration token, который выдаётся в настройках Notion; OAuth-флоу
здесь нет намеренно (см. ниже).

### Демо

```bash
# weather: агент берёт город из профиля, геокодит его и смотрит прогноз
curl -s -X POST http://localhost:3000/api/agent/run -H 'Content-Type: application/json' \
  -d '{"task":"спланируй тренировку на завтра с учётом погоды"}'

# filesystem: агент кладёт копию плана в plans/<дата>.md
curl -s -X POST http://localhost:3000/api/agent/run -H 'Content-Type: application/json' \
  -d '{"task":"составь план питания на завтра и сохрани его ещё и в отдельный файл в папке plans"}'

# notion (только если в .env есть NOTION_TOKEN)
curl -s -X POST http://localhost:3000/api/agent/run -H 'Content-Type: application/json' \
  -d '{"task":"составь план на неделю и сохрани его страницей в мой Notion"}'
```

В трейсе первого прогона видно, как это выглядит изнутри:

```
[markdown-health] read_profile
[markdown-health] read_recent_logs
[weather]         openmeteo_search_locations
[weather]         openmeteo_get_forecast
[local]           suggestWorkoutTemplate
[markdown-health] save_health_plan
```

А в плане — ссылка на настоящий прогноз: «Завтра в Казани сухо, 13–19 °C, дождь возможен
только после 19:00 — лучший день, чтобы сделать третью тренировку недели на воздухе».
Город приехал из `data/profile.md`; ни координат, ни названия города в коде нет.

### Guardrails: промпт — просьба, конфиг — стена

Это главный принцип раздела, и держится он на том, что **уровня защиты два, и верхний
без нижнего не работает**. Промпт можно не выполнить: модель вправе решить, что записать
файл повыше папкой будет полезнее. Конфиг обойти нечем — того, чего нет в списке тулов
или за границей разрешённых папок, не существует.

| Сервер | Стена (конфиг) | Просьба (промпт) |
|---|---|---|
| `filesystem` | папки `data/` и `plans/` заданы **в аргументах запуска сервера**; из 14 тулов коучу видны 3 | «файлы — только в `plans/`, имя `plans/<дата>.md`» |
| `notion` | права самой интеграции: в Notion ей выдана одна страница «Wellness» | «создавай страницу только внутри Wellness» |
| `weather` | не нужна | «планируешь улицу — сперва посмотри прогноз» |

Про `filesystem` стоит сказать отдельно, потому что стена здесь проверяемая. Список папок
живёт в `args`, то есть на стороне сервера, и клиент расширить его не может: единственный
механизм, которым MCP-клиент мог бы переназначить папки, — Roots, а Agents SDK его
не поддерживает. Сервер сообщает об этом сам при старте:

```
Client does not support MCP Roots, using allowed directories set from server args: [
  '…/03-agent-OS/data',
  '…/03-agent-OS/plans'
]
```

**`weather` — пример того, что не все серверы одинаково опасны.** Он read-only по природе:
самое плохое, что он может сделать, — вернуть неверный прогноз. Гейта на нём нет, потому
что гейт нужен там, где есть что испортить, а не везде подряд. Симметрично раздавать
ограничения — значит перестать понимать, зачем они.

### Гейт распространяется и на чужие серверы

Иначе он был бы декоративным: `write_file` из `filesystem` пишет на диск ровно так же,
как наш `save_health_plan`, и коуч мог бы положить **неодобренный** план в `plans/`
в обход ворот. Поэтому у записи в конфиге есть отдельное поле:

```ts
tools:      ['list_directory', 'read_text_file'],  // видны всегда
writeTools: ['write_file'],                        // видны только после approve
```

Механизм тот же `toolFilter`, что всегда держал `save_health_plan`, — изменилось лишь то,
что список приезжает данными из конфига, а не зашит в код. В трейсе это видно по порядку:
все вызовы `[filesystem] write_file` стоят **после** `save_health_plan`, то есть в
закрепляющем заходе, — за весь цикл ни одной записи.

Одна честная оговорка. Для `data/output.md` харнесс сверяет записанное с планом по тексту
и перезаписывает сам, если коуч передал в тул пересказ вместо плана (это бывает регулярно:
`Коуч сохранил не тот текст — план перезаписал харнесс`). **У копии в `plans/` такой
страховки нет** — она потребовала бы обёртки над чужим тулом, а обёрток мы здесь
не пишем. Поэтому файл в `plans/` может оказаться короче: авторитетная копия — всегда
`data/output.md`.

### Отключить сервер

`enabled: false` — и его тулов у агента нет. Без ошибок, без правок кода:

```
enabled: true    MCP-серверы (3): markdown-health, filesystem, weather
enabled: false   MCP-серверы (2): markdown-health, filesystem
```

### Что ещё можно было бы подключить

Список серверов большой, и вот три, которые в этом проекте напрашиваются, — но
не подключены:

- **Google Calendar** — разложить тренировки по календарю и не ставить их на занятые
  вечера. **Вынесен за скобки: требует OAuth-флоу** с редиректом и обновлением токенов,
  а это уже не «положить ключ в `.env`», а отдельная авторизационная механика. Граница
  этого проекта проходит ровно здесь: максимум — токен из `.env`.
- **Database (Postgres MCP)** — держать дневник и вес в таблице вместо markdown, и дать
  ревьюеру считать динамику запросом, а не пересказом.
- **Web Search (Brave / Tavily MCP)** — проверять утверждения о питании по источникам,
  а не по памяти модели. Оба требуют API-ключа, но ключ — это `.env`, а не OAuth.

## OS: модули, роутер, память

Поверх прогона стоит тонкий слой, который решает три вопроса: какой это запрос, какой
конфигурацией его вести и что запомнить после.

```
task → classifyIntent → runHealthAgent(с модулем) → memory update
```

**Модуль — это конфигурация, а не агент.** `{ name, description, promptFile, tools }`:
промпт-наслойка поверх `healthCoach.v9` и список тулов, которые видит коуч. Агент
остаётся один — `createCoach`, — и модуль меняет два его аргумента из трёх.
Мультиагентной оркестрации здесь нет намеренно: handoffs и подагенты завели бы восемь
наборов промптов и восемь мест, где может разъехаться формат плана.

**Наслойка, а не замена.** Формат плана разбирают три независимых парсера
(`app/plan-markdown.tsx`, `src/mcp/markdownBlocks.ts` и `sourceText` в `src/skills/shopping.ts`),
поэтому он описан один раз — в базовом промпте. Модульный файл говорит только про свою
тему: с чего начинать, что искать в базе знаний, какие величины ставить в «На что смотреть».

**Модуль может только отнимать тул.** Сужение исполняется тем же `toolFilter`, который
держит гейт, и стоит **после** allowlist сервера — дать тул, которого нет
в `servers.config.ts`, модулем нельзя. Тулы записи выведены из-под сужения: ими командует
только гейт, иначе модуль, забывший `save_health_plan`, молча ломал бы сохранение.
Проверяется это единственным способом:

```bash
npm run mcp:inspect -- --module recipes   # что модуль отнимает сверх базовой политики
```

**Роутер — один заход и одна строка ответа.** `nutrition 0.8`. Порог `MODULE_CONFIDENCE`
живёт в коде, и в промпте роутера его нет вовсе — прямой урок `APPROVE_SCORE`. Любая
осечка разбора сводится к `general`: за ним стоит рабочее поведение по умолчанию,
а за падением не стоит ничего. Модель роутера отдельная (`ROUTER_MODEL` с откатом
на `DEEPSEEK_MODEL`): платить за классификацию как за план незачем.

**Safety Reviewer обязателен для каждого модуля и ни одним не параметризуется.** Триаж,
ревьюер, порог одобрения и гейт живут внутри `runHealthAgent` и про модуль не знают.
Специализация не может ослабить проверку, потому что не имеет к ней доступа. Закреплено
комментарием в `src/os/runOS.ts`, комментарием в `src/os/modules/index.ts` и кейсом
`evals/cases/module-recovery-stop.json` — задачей, которую защитный контур обязан
остановить при выбранном модуле.

**Память пополняется только после `approve`, и пишет её харнесс, а не агент.**
`append_daily_log` и `update_preferences` коучу не даются никогда — их зовёт
`src/os/memory.ts` напрямую через MCP, той же идиомой, которой кнопка «в Notion» ходит
на сервер мимо модели. В дневник едет блок с подзаголовком `### Предложено агентом`:
дневник — доказательная база ревьюера, и без явной пометки следующий прогон прочитал бы
намерение как факт. В `data/preferences.md` фраза человека едет **дословно**, и только
когда в задаче есть явный сигнал («запомни», «понравилось») — ловят его ключевые слова
в коде, а не решение модели.

**У `check_habit` гейта нет — это единственное явное исключение в проекте.** Отметка
привычки это факт, который человек сообщил в запросе, а не запись плана, и ждать
одобрения плана ей нечего. Цена признана: прогон, завёрнутый ревьюером, всё равно может
оставить след в `data/habits.md`, и тезис «пока план не одобрен, на диск не ложится
ничего» с этого момента не безоговорочен.

## Контракт API

`POST /api/agent/run` с телом `{ "task": "..." }` возвращает:

```ts
{
  plan: string | null   // null при needs_human_professional
  review: {
    verdict: 'approve' | 'revise' | 'needs_human_professional'
    score: number       // 0–10
    issues: string[]
  }
  rounds: number        // сколько раундов реально прошло; 0 — задачу завернул триаж
}
```

`score` модель не называет — харнесс складывает его из пяти осей `breakdown`, по 0–2 балла
за ось. Одобрение ниже 8 баллов код понижает до `revise` сам, не полагаясь на промпт.

Ошибки: `400` — пустая задача или неразбираемое тело; `500` — нет ключа либо ревьюер
дважды вернул невалидный JSON.

`data/output.md` перезаписывается **только** при вердикте `approve` — как и в CLI-версии.

### `POST /api/chat` — тот же прогон, рассказанный по ходу

Принимает `{ messages }` в формате AI SDK и берёт задачей текст **последнего**
пользовательского сообщения. Прошлые сообщения не читаются: `runHealthAgent` принимает
строку, а склеить в неё транскрипт значило бы протащить его через триаж и ревьюера,
которые судят по полю «Задача». Памяти между прогонами у агента поэтому нет, и это
осознанно — история живёт только на экране.

Отдаёт SSE-поток из трёх видов частей:

| Часть | Когда | Что несёт |
|---|---|---|
| `data-step` | по ходу прогона | шаг таймлайна: тул, раунд, ревью, вердикт, превью черновика |
| `text-delta` | после цикла | готовый план по строкам |
| `data-result` | в конце | вердикт, оценка, раунды, тулы, retrievals, версии промптов, время |

Шаги приходят со стабильным `id` и **обновляются на месте**: `running → done` у тула,
растущее превью у черновика. Порядок реального прогона выглядит так:

```
plan-1    running  first
tool-1    done     read_profile
tool-2    done     read_recent_logs
tool-3    done     list_recipes
tool-4    done     searchKnowledge
plan-1    done     черновик 2157 зн.
review-1  running
review-1  done     approve 9/10
finalize  running
tool-5    done     save_health_plan
finalize  done
```

**План стримится после цикла, а не во время.** Наружу уезжает `finalRound` — последний
одобренный раунд, а он не обязан быть последним написанным. Текст, который течёт дельтами
во время раунда, — черновик, и живёт он только в строке таймлайна; в сообщение чата едет
`result.plan`. Так текст сообщения всегда ровно тот, что признан итогом.

При `needs_human_professional` текстовых частей нет вовсе: плана не существует, и чат
показывает карточку «Требуется специалист» с причиной.

## Как дебажить агента

Три команды, одна цепочка: **trace → replay → eval**. Смотреть на один прогон, сравнить
два прогона одной задачи, проверить систему целиком.

**Trace.** Каждый прогон — из UI, из replay, из eval — кладёт себя в `runs/run-<время>.json`:
задача, версии промптов, модель, все раунды с выдержкой плана и вердиктом, вызванные тулы,
итоговая оценка, время. Отвечает на вопрос «что вообще происходило»: сколько было раундов,
на чём ревьюер упирался, звал ли коуч тулы или сочинял из головы.

Рядом с `toolCalls` едет `toolSources` — карта «имя тула → сервер, который его дал».
По ней видно не только что агент звал, но и откуда это взялось: наш `markdown-health`,
чужой `weather` или локальный навык. Отдельным полем, а не префиксом внутри имён: имена
в `toolCalls` сравниваются с константами, и трейсы прошлых прогонов должны читаться
прежним `replay`. Это же поле рисует пометки `[weather]`, `[filesystem]`, `[local]`
в блоке «что сделал агент» в интерфейсе. Папка в `.gitignore`,
кроме `runs/run-example.json` — это настоящий трейс, оставленный в репо как образец формата
и как то, с чего можно запустить `replay` на свежем клоне (`runId` внутри — от прогона,
имя файла — от роли).

Запись трейса не может уронить прогон: не записалось — строка в логе, и всё едет дальше.

**Replay.** Берёт задачу из трейса и гонит её через сегодняшний код:

```bash
npm run replay runs/run-2026-08-17T10-00-00-000Z.json
```

Печатает две колонки, «было» и «стало»: вердикт, оценка, раундов, промпты, модель, тулы,
время; стрелка `←` у строк, которые разошлись. Это ответ на вопрос «правка промпта сделала
лучше или просто иначе». Правишь `prompts/`, переключаешь `ACTIVE_PROMPTS`, меняешь
`DEEPSEEK_MODEL` — и переигрываешь старый прогон.

**Eval.** Пять кейсов в `evals/cases/*.json`, у каждого записано, чем прогон обязан кончиться:

```bash
npm run eval                      # все пять
npm run eval bad-medical-request  # только названные
```

Формат кейса — `{ name, task, expect: { verdict, minScore? } }`. Четверо ждут `approve`
с оценкой не ниже 8, а `bad-medical-request` ждёт `needs_human_professional`: это тест
защитного контура, и проходит он **только когда агент останавливается** и плана не выдаёт.
Скрипт печатает таблицу PASS/FAIL и возвращает ненулевой код, если что-то упало.

Именно этот кейс поймал регрессию `safetyReviewer.v5`: промпт утверждал, что исходной
задачи ревьюер не получает, — и запрос «подбери дозировку препаратов» был одобрен, потому
что правильный отказ коуча читался как хороший план. Отсюда триаж: вердикт «нужен живой
специалист» относится к запросу, и спрашивается он про запрос, до коуча и без плана.

Проверяется исход, а не текст: план модель каждый раз пишет свой, а «на такую просьбу
агент обязан остановиться» — свойство системы, и ломается оно правкой промпта незаметно.

Две вещи, которых стоит ждать. Прогоны настоящие и идут по одному, так что полный
`npm run eval` — это десятки минут и заметный расход ключа. И они не изолированы от
`data/`: одобренный план перезаписывает `data/output.md` (а где есть закупка — и
`data/shopping.md`) ровно так же, как прогон из UI. Так и задумано — eval проверяет тот
путь, которым ходит человек, а не его облегчённую копию.

## Почему index.ts удалён, а не оставлен CLI-враппером

Условие задачи допускало оба варианта. Выбрано удаление: приложение веб-овое, и второй
вход существовал бы только ради самого себя. Враппер пришлось бы держать в рабочем
состоянии — свой разбор аргументов, свой формат вывода, свой способ подхватить `.env`, —
а проверялся бы он реже, чем UI, и первым бы протух.

Логика при этом никуда не делась: она вся в `runHealthAgent`, который ничего не знает
про Next.js — только `node:fs`, `@openai/agents` и `zod`. Вернуть CLI — это файл на
двадцать строк поверх той же функции, если он однажды понадобится.

## Что изменилось при переезде с CLI на веб

Промпты, схема вердикта, разбор JSON с одним ретраем и тело цикла перенесены дословно.
Отличий ровно четыре, и все они вынуждены сменой среды запуска:

1. **Пути к данным.** Было `dirname(fileURLToPath(import.meta.url))`, стало
   `join(process.cwd(), 'data')`. После сборки Next модуль лежит внутри `.next/`,
   и путь от файла указал бы не туда.

2. **Загрузка `.env`.** `process.loadEnvFile()` убран: Next читает `.env` сам, до того
   как выполнится код приложения. Вызывать его из харнесса было бы поздно — ESM вычисляет
   импорты до тела модуля, так что агенты успели бы прочитать `process.env` раньше.

3. **Отсутствие ключа — исключение, а не `process.exit(1)`.** На сервере падение процесса
   уронило бы весь дев-сервер, поэтому харнесс бросает ошибку, а роут отдаёт `500` с текстом.
   Настройка клиента DeepSeek стала ленивой и выполняется один раз при первом прогоне.

4. **Исход «3 раунда без одобрения» стал возвращаемым значением.** CLI просто печатал строку
   и завершался. Теперь харнесс возвращает последний план с вердиктом `revise`, а UI
   показывает план вместе с пометкой, что он не одобрен и в `data/output.md` не сохранён.
   Побочные эффекты при этом те же, что и в CLI: файл не трогается.
