# Чат со стримингом: события харнесса, таймлайн этапов, сессия прогонов

Дата: 2026-08-20 · статус: утверждён к реализации

## Зачем

Сейчас страница — форма: textarea, кнопка, секундомер и тишина на 40–120 секунд, после
которой разом появляется вся сцена вердикта. Пользователь не видит ни того, что коуч
читает профиль, ни того, что он ищет в базе знаний, ни того, что ревьюер завернул первый
план и коуч пишет второй. Всё это уже происходит и всё это уже пишется в трейс — просто
показывается постфактум и в свёрнутом блоке.

Задача — заменить форму чатом, в котором ход прогона виден по мере работы: тулы
появляются в момент вызова, раунды и вердикты — в момент, когда они случились, а
финальный план стримится текстом. История прогонов остаётся на экране в пределах сессии,
и сессию можно начать заново.

Границы намеренно узкие: харнесс не переписывается — в него добавляется эмиссия событий;
персиста нет; мульти-чатов нет; памяти между прогонами у агента нет.

## Что меняется, а что нет

| | Сейчас | После |
|---|---|---|
| Ввод задачи | textarea + кнопка «Собрать план» | поле чата, история сообщений на странице |
| Ход прогона | секундомер `00:47` | таймлайн: тулы, раунды, вердикты по мере работы |
| Финальный план | появляется целиком | стримится текстом после цикла |
| Вердикт и оценка | сцена «ворота → стойки → экспонат» | карточка под планом, минимальный CSS |
| Трейс | `<details>` внутри ворот | `<details>` в подвале сообщения |
| Прошлые прогоны | пропадают | остаются в чате, таймлайн свёрнут |
| `/api/agent/run` | единственный роут | жив и не тронут |
| `runHealthAgent` | `(task, RoundLimits)` | `(task, RoundLimits & { onEvent? })` |
| `npm run eval` | работает | идёт по прежнему, не-стриминговому пути |

## Главное архитектурное следствие: план стримится после цикла

`finalRound()` в `src/harness/score.ts` отдаёт **последний одобренный** раунд, а не
последний. При доборе до `minRounds` цикл продолжается и после `approve`, и если раунд
добора вышел хуже, наружу уезжает предыдущий план. Значит, пока цикл не кончился,
неизвестно, какой из написанных планов финальный, и «стримить финальный план токен за
токеном» в буквальном смысле невозможно.

Отсюда разделение, которое проходит через весь дизайн:

- **дельты раунда** — это черновик. Едут в строку таймлайна «пишет план» живым превью
  и умирают вместе с раундом;
- **финальный план** — берётся из `result.plan` **после** `await runHealthAgent(...)`
  и стримится в текстовую часть сообщения чанками.

Текст ассистентского сообщения поэтому всегда ровно `final.plan` — по построению, а не
по совпадению. Порядок на экране: таймлайн живёт → план стримится → карточка вердикта.

## Модули

### `src/harness/events.ts` (новый)

Словарь событий прогона и эмиттер. Идиома копируется с `createGate()` и
`createRetrievalLog()`: объект создаёт харнесс на прогон, вызывающая сторона только пишет.

```ts
import type { Review } from './validateReview';

export type AgentEvent =
  /** Триаж вынес решение. blocked = true — коуч не запускался, раундов ноль. */
  | { type: 'triage'; blocked: boolean; reason: string | null }
  /** Раунд начался. kind различает «первый», «по замечаниям» и «добор до минимума». */
  | { type: 'round-start'; round: number; kind: 'first' | 'revise' | 'reinforce' }
  /** Коуч позвал тул. args — сырая строка аргументов, харнесс её не разбирает. */
  | { type: 'tool'; round: number; name: string; args: string }
  /** Кусок текста плана этого раунда. Черновик: финальным он станет не обязательно. */
  | { type: 'plan-delta'; round: number; delta: string }
  | { type: 'review-start'; round: number }
  | { type: 'review-done'; round: number; review: Review }
  /** Закрепляющий заход: гейт открыт, коуч сохраняет. round здесь нет — он вне цикла. */
  | { type: 'finalize' };

export type AgentEventHandler = (event: AgentEvent) => void;

export type Emitter = {
  send(event: AgentEvent): void;
  /** Есть ли слушатель. Читает только streamCoach — чтобы решить, стримить ли заход. */
  readonly active: boolean;
};

export function createEmitter(onEvent?: AgentEventHandler): Emitter;
```

Решения и их причины:

- **Без `onEvent` `send` — пустая функция.** Поэтому в цикле нет ни одного `if (onEvent)`:
  код читается одинаково для evals и для чата, и расхождение поведения между ними
  невозможно по построению.
- **События `done` нет.** Роут получает `HealthAgentResult` возвратом — `rounds`,
  `finalScore`, `toolSources`, `retrievals`, `promptVersions`, `durationMs` приезжают
  оттуда. Union описывает только ход прогона; итог остаётся возвращаемым значением,
  и существующий контракт не раздваивается.
- **`review-done` несёт `Review` целиком**, а не выборку полей: тип уже есть, и копия
  его формы разъехалась бы при первой же правке `BreakdownSchema`.
- **`args` — сырая строка.** Харнесс не парсит аргументы конкретных тулов. Запрос
  из `searchKnowledge` достаёт консоль, которая и так тул-специфична (`SEARCH_KNOWLEDGE`,
  `TOOL_LABELS`, `NOTION_CREATE_PAGE`).

### `src/harness/streamCoach.ts` (новый)

Один заход коуча — стриминговый или обычный, в зависимости от того, слушает ли кто-то.

```ts
export async function runCoach(
  coach: Agent,
  input: string,
  emitter: Emitter,
  round: number,
): Promise<{ newItems: RunItem[]; finalOutput: unknown }>;
```

- `emitter.active === false` → `return run(coach, input, { maxTurns: MAX_TURNS })`.
  Ровно тот вызов, что стоит в цикле сейчас. По этому пути идут evals, replay
  и `/api/agent/run`.
- иначе → `await run(coach, input, { maxTurns: MAX_TURNS, stream: true })`, затем
  `for await` по `RunStreamEvent`:
  - `run_item_stream_event`, `name === 'tool_called'`, `rawItem.type === 'function_call'`
    → `emitter.send({ type: 'tool', round, name, args })`
  - `raw_model_stream_event` с текстовой дельтой
    → `emitter.send({ type: 'plan-delta', round, delta })`
  - `await stream.completed`, вернуть `{ newItems: stream.newItems, finalOutput: stream.finalOutput }`

Возврат совместим по форме с `RunResult`, поэтому `collectToolCalls(coachOutput)`
и `String(coachOutput.finalOutput ?? '').trim()` в цикле не меняются. Тулы не считаются
дважды: `toolCalls` по-прежнему собирается из `newItems` после захода, а события `tool`
идут мимо этого массива и служат только показу.

**Это второе и последнее место, где харнесс знает внутренности SDK.** `CLAUDE.md` сейчас
утверждает, что `toolCalls.ts` — единственное; тезис уточняется: таких файла два,
стриминговый и не-стриминговый, ответственность одна, и граница проходит по ним.
Расширять её на третий файл нельзя.

### `src/harness/runHealthAgent.ts` (правки)

Сигнатура — расширение существующего мешка опций, третьего параметра не появляется:

```ts
export type RunOptions = RoundLimits & { onEvent?: AgentEventHandler };

export async function runHealthAgent(
  task: string,
  { minRounds = DEFAULT_MIN_ROUNDS, maxRounds = DEFAULT_MAX_ROUNDS, onEvent }: RunOptions = {},
): Promise<HealthAgentResult>;
```

Все существующие вызовы (`app/api/agent/run/route.ts:19`, `scripts/eval.ts:88`,
`scripts/replay.ts:60`) передают только `task`, поэтому расширение для них невидимо.

Точки эмиссии — все в уже существующих местах, логика не двигается:

| Где | Событие |
|---|---|
| после `triageTask(...)` | `triage` с `blocked` и `reason` |
| в начале итерации цикла | `round-start`; `kind` = `first` при `previous === null`, `reinforce` при `previous.review.verdict === 'approve'`, иначе `revise` |
| вместо `run(coach, buildCoachInput(...))` | `runCoach(coach, ..., emitter, round)` |
| перед `validateReview(...)` | `review-start` |
| после `enforceApproveThreshold(...)` | `review-done` с итоговым `Review` — **после** понижения порога, иначе в таймлайне встанет `approve`, которого прогон не признал |
| перед закрепляющим заходом | `finalize` |
| вместо `run(coach, buildFinalizeInput(...))` | `runCoach(...)` — иначе `save_health_plan`, `generateShoppingList` и `write_file` не попадут в таймлайн |

Цикл, гейт, порог одобрения, выбор `finalRound`, страховка `planMatchesDisk` и `traceRun`
не меняются ни строкой. Порядка тридцати строк на файл в 414.

## Роут: `app/api/chat/route.ts` (новый)

```ts
export const runtime = 'nodejs';
export const maxDuration = 300;
```

`nodejs` — по той же причине, что у `/api/agent/run`: агенты читают и пишут `data/`
и поднимают дочерние процессы. `maxDuration` — потому что прогон идёт до нескольких минут,
а дефолтный потолок короче.

Тело: `messages` из `useChat`. Задача — текст **последнего** пользовательского сообщения.
Прошлые сообщения роут не читает: агент их не видит (см. «Памяти между прогонами нет»).

```ts
const stream = createUIMessageStream<WellnessUIMessage>({
  execute: async ({ writer }) => {
    const result = await runHealthAgent(task, {
      onEvent: (event) => writeStep(writer, event),
    });

    if (result.plan) {
      writer.write({ type: 'text-start', id: textId });
      for (const chunk of chunks(result.plan)) {
        writer.write({ type: 'text-delta', id: textId, delta: chunk });
      }
      writer.write({ type: 'text-end', id: textId });
    }

    writer.write({ type: 'data-result', id: `${runId}:result`, data: toResultData(result) });
  },
  onError: (error) => (error instanceof Error ? error.message : 'Неизвестная ошибка.'),
});

return createUIMessageStreamResponse({ stream });
```

### Форма data-частей

Шаги едут **одним** типом `data-step` с полем `kind`, а не шестью отдельными типами:
таймлайн — плоский упорядоченный список, и разбирать его так проще, чем сшивать
из шести коллекций.

```ts
export type StepKind = 'triage' | 'tool' | 'plan' | 'review' | 'finalize';

export type Step = {
  kind: StepKind;
  status: 'running' | 'done';
  round: number | null;
  /**
   * Только у kind: 'plan'. Различает «пишет план», «переписывает по замечаниям»
   * и «усиливает одобренный» — это и есть отдельный шаг «Revising (раунд N)»
   * из требований, а не подпись, вычисленная в консоли по номеру раунда.
   */
  phase?: 'first' | 'revise' | 'reinforce';
  tool?: { name: string; args: string };
  draft?: { chars: number; tail: string };
  review?: Review;
  blocked?: { reason: string };
};

export type ResultData = {
  verdict: Review['verdict'];
  score: number;
  issues: string[];
  rounds: { round: number; verdict: Review['verdict']; score: number }[];
  finalRound: number;
  toolCalls: string[];
  toolSources: Record<string, string>;
  retrievals: Retrieval[];
  promptVersions: PromptVersions;
  durationMs: number;
  improved: boolean;
};

export type WellnessUIMessage = UIMessage<never, { step: Step; result: ResultData }>;
```

`ResultData` — не `HealthAgentResult`: поле `plan` из него убрано намеренно. План уезжает
текстовой частью, и вторая его копия в data-части означала бы два источника истины
для одного текста. `rounds` урезаны до вердикта и оценки — тексты планов раундов
консоли не нужны, а при `needs_human_professional` их там и нет.

### Идентификаторы и реконсиляция

Каждый шаг пишется со стабильным `id`, поэтому повторная запись **обновляет** часть
на месте, а не добавляет вторую: `running → done` для тула, `review-start → review-done`
для ревью, растущее превью для черновика.

`writeStep` — единственное место, где `AgentEvent` превращается в `data-step`, и вся
таблица соответствия живёт в нём:

| Событие | `id` | Что пишется |
|---|---|---|
| `triage` (blocked) | `<run>:triage` | `kind: 'triage'`, `status: 'done'`, `blocked.reason` |
| `triage` (пропущен) | — | ничего: пройденный триаж — не шаг, а отсутствие препятствия |
| `round-start` | `<run>:plan-<round>` | `kind: 'plan'`, `status: 'running'`, `round`, `phase` из `kind` события |
| `tool` | `<run>:tool-<n>` | `kind: 'tool'`, `status: 'done'`, `tool.name`, `tool.args` |
| `plan-delta` | `<run>:plan-<round>` | тот же шаг, обновляется `draft` (троттлинг ниже) |
| `review-start` | `<run>:plan-<round>` | `status: 'done'` — раунд дописан |
| `review-start` | `<run>:review-<round>` | `kind: 'review'`, `status: 'running'` |
| `review-done` | `<run>:review-<round>` | `status: 'done'`, `review` |
| `finalize` | `<run>:finalize` | `kind: 'finalize'`, `status: 'running'` |
| конец `execute` | `<run>:finalize` | `status: 'done'`, если шаг заводился |

`<n>` у тулов — сквозной счётчик по прогону, а не по раунду: повторный `read_profile`
во втором раунде обязан стать новой строкой, а не обновить строку из первого.

`<run>` — идентификатор прогона, который роут заводит на каждый запрос (`crypto.randomUUID()`
или счётчик — неважно, важна уникальность в пределах сессии). Префикс не бесплатная
перестраховка, а страховка от единственного риска, который история прогонов создаёт
в протоколе: если реконсиляция `data-*` частей скоупится не на текущее сообщение, а шире,
третий прогон затрёт вердикт первого. Проверять это живым багом дорого, префикс стоит
нисколько.

### Живое превью черновика

`plan-delta` копится на сервере и переписывает часть `plan`-шага **не чаще раза
в 150 мс**, отдавая `{ chars, tail }` — счётчик знаков и последние ~200 символов.
Перезапись накопленного текста целиком на каждую дельту дала бы квадратичный трафик:
план в 3 КБ при посимвольных дельтах — это сотни килобайт на воздух. Хвоста и счётчика
для сорока секунд ожидания достаточно: черновик всё равно будет переписан или отброшен.

Троттлинг обязан отдавать последнее состояние: если раунд кончился внутри окна в 150 мс,
финальная запись шага (`status: 'done'` по `review-start`) делается сразу, без ожидания
таймера, иначе последняя порция черновика потеряется на самом заметном месте.

### Как стримится финальный план

`result.plan` режется **по строкам** (`split(/(?<=\n)/)`), и каждая строка уходит одной
`text-delta` с паузой в 12 мс. По строкам, а не по символам, потому что `renderPlan`
разбирает markdown построчно: посимвольный стрим показывал бы `#` и `**` как сырой текст
до конца строки. Пауза нужна, чтобы стрим читался как печать, а не как мгновенная вставка;
на длинном плане это добавляет секунду-полторы — приемлемо после минуты работы цикла.

## UI

### `app/chat.tsx` (новый)

```ts
const { messages, sendMessage, status, setMessages } = useChat<WellnessUIMessage>({
  transport: new DefaultChatTransport({ api: '/api/chat' }),
});
```

Пользовательское сообщение — пузырь с текстом. Ассистентское — запись прогона, сверху вниз:

1. **таймлайн** из `data-step`-частей в порядке прихода;
2. **план** — текстовая часть через существующий `renderPlan`;
3. **карточка вердикта**: слово, оценка, замечания;
4. **подвал**: `<details>` с трейсом, кнопки «скопировать» и «в notion».

При `needs_human_professional` пунктов 2 и 4 нет вовсе: вместо плана — карточка
«Требуется специалист» с `issues`. Это то же защитное правило, что в харнессе
(`plan: null`, `redactPlans`), только показанное.

Строка тула несёт вид источника — `[mcp]`, `[rag]`, `[навык]`. Логика `kindOf` переносится
из `agent-console.tsx` как есть: RAG проверяется первым и по имени, потому что тул
локальный и в `toolSources` его нет. Для `searchKnowledge` строка подменяется на запрос —
он парсится из `args` события `tool` живьём, не дожидаясь конца раунда.

### Сессия

Сессия — это состояние `useChat` на странице, и ничего кроме.

- Каждый прогон даёт свою пару сообщений; ассистентское держит полную запись прогона.
  Ничто между прогонами не переиспользуется.
- Кнопка **«новая сессия»** в рейке: `setMessages([])` плюс сброс локального состояния
  (Notion, «скопировано», превью). Заблокирована, пока прогон идёт. Диск не трогает:
  `data/output.md`, `data/shopping.md` и `runs/*.json` — результаты работы, а не состояние
  чата, и стирать их по «начать с нуля» было бы сюрпризом.
- Перезагрузка страницы = новая сессия. Прямое следствие запрета на персист, и это
  сказано в интерфейсе: иначе выглядит как потеря данных.

### Что история ломает, если её просто оставить лежать

**Завершённые таймлайны сворачиваются.** Пять прогонов по десять тул-строк — экран,
по которому невозможно двигаться. Отработавший таймлайн схлопывается в строку
`▸ 12 шагов · 2 раунда · 47 с` и разворачивается кликом; живой развёрнут. План и вердикт
на виду всегда — они и есть ответ.

**Кнопка «в notion» остаётся только на последнем одобренном плане.** Это следствие защиты,
а не косметика: `/api/plan/notion` сверяет присланный текст с `data/output.md`, где лежит
план последнего одобренного прогона. Нажать её под планом первого прогона после того,
как третий получил `approve`, — гарантированный `409`. Кнопка, которая всегда возвращает
ошибку, хуже отсутствующей. «Скопировать» остаётся везде: она ничего не сверяет.

**Автоскролл прилипает только у дна.** Пользователь ушёл вверх читать прогон №1 — страница
за ним не тянется; вместо этого внизу появляется «↓ вниз». Порог — примерно 100 px
от низа. Без истории это была бы придирка, с историей — обязательное поведение.

**Инпут заблокирован, пока `status !== 'ready'`.** Два параллельных прогона делили бы
`data/output.md` и гейт, а гейт живёт на прогон.

| `app/globals.css` | вырезаются `hero`, `console`, `presets`, `gate`, `struts`, `exhibit`, `score`, `issues`, `trace`, `tools`, `found` (~600 строк); остаются токены, `shell`/`rail`/`foot` и блок `prefers-reduced-motion`; добавляются `chat`, `msg`, `timeline`, `step`, `paper`, `verdict` (~250 строк) |
| `app/plan-markdown.tsx` | **не трогается** |

`plan-markdown.tsx` остаётся как есть намеренно. `CLAUDE.md` предупреждает, что его формат
связан с промптом коуча и с `markdownBlocks.ts`; переименование классов `paper__*`
расширило бы правку на промпт и на конвертер Notion. Под существующие имена классов
пишется новый CSS.

Пресеты переживают переход как пустое состояние чата: это единственная подсказка новичку,
что вообще можно попросить.

## Зависимости

```
+ ai
+ @ai-sdk/react
```

Провайдеры (`@ai-sdk/openai` и прочие) **не ставятся**: модель ходит через `@openai/agents`
с подменённым клиентом DeepSeek, и SDK здесь только транспорт и протокол сообщений.
Он берётся ради двух вещей, которые пришлось бы писать руками: реконсиляции data-частей
по `id` и сборки текстовых дельт в сообщение.

`next.config.ts` не меняется: `serverExternalPackages` перечисляет пакеты с node-спецификой,
а `ai` и `@ai-sdk/react` бандлятся нормально.

## Памяти между прогонами нет

`runHealthAgent(task: string)` истории не принимает, а переписывать харнесс запрещено.
Единственным способом дать агенту память была бы склейка транскрипта в строку `task` —
но `task` уезжает не только коучу: `runHealthAgent.ts:256` кладёт его в `## Задача`
ревьюеру, `triageTask()` судит по нему же, и он целиком пишется в трейс. Транскрипт
в поле задачи прошёл бы прямо через оба защитных контура, промпты под такой вход
не писались, а `replay` старых трейсов начал бы сравнивать неравное.

Поэтому каждое сообщение — независимый прогон, и `task` равен ровно тому, что набрал
человек. Следствие видно пользователю: «а теперь то же без рыбы» не сработает, задачу
надо переформулировать целиком. Это осознанная цена, а не недосмотр.

## Риск: отдаёт ли DeepSeek текстовые дельты

Единственное непроверенное место дизайна. `@openai/agents` работает с DeepSeek через
`chat_completions` (Responses API у DeepSeek нет), и приходят ли оттуда
`raw_model_stream_event` с текстом — по докам должно, но живьём не проверялось.

**Первый шаг реализации — щуп на двадцать строк**, который поднимает коуча, гоняет
`run(..., { stream: true })` и печатает типы пришедших событий. До всякого UI.

Если дельт нет, падает только `plan-delta`. События `tool` генерирует SDK, а не модель,
и они придут в любом случае — живой таймлайн тулов, раундов и вердиктов остаётся целиком.
Исчезает превью черновика в строке «пишет план»: вместо хвоста текста там остаётся
счётчик времени. Финальный план стримится как описано выше и без изменений, потому что
он и так берётся из `result.plan` после цикла. Обходных путей в этом случае не строится —
результат щупа сообщается, и дизайн правится явно.

## Чего в этой работе нет

- тестов и TDD — по `CLAUDE.md`;
- персиста истории чата: ни БД, ни `localStorage`, ни `sessionStorage`;
- мульти-чатов: «новая сессия» обнуляет единственный чат, а не заводит второй;
- памяти агента между прогонами;
- отмены прогона на полпути: `AbortSignal` до `runHealthAgent` не доходит, а MCP-процессы
  гасятся в `finally` вокруг цикла;
- изменений в промптах, evals, RAG, MCP-слое и схеме БД;
- UI-библиотек.

## Осознанные отступления

**`streamCoach.ts` — второе место, знающее внутренности SDK.** `CLAUDE.md` утверждает, что
`toolCalls.ts` единственное. Иначе никак: живой тул-вызов существует только как событие
стрима, и достать его без разбора `RunStreamEvent` нельзя. Граница переописывается на два
файла, и оба перечислены в «Что легко сломать».

**Старая сцена вердикта удаляется целиком.** «Ворота → стойки → экспонат», шкала на десять
делений, «бумага» и цвет-как-вердикт — проработанная система, и вместе с ней уезжает
связанный пласт `CLAUDE.md`. Решение принято сознательно: чат с двумя поверхностями
и сценой внутри пузыря — это не «аккуратный минимальный CSS», а два дизайна в одном файле.

**`/api/agent/run` остаётся живым, хотя после переключения UI им никто не пользуется.**
Требование явное: не-стриминговый роут должен продолжать работать. Он же — страховка,
если стриминговый путь окажется сломан.

## Что легко сломать (дописать в `CLAUDE.md`)

- **`AgentEvent` — контракт между тремя слоями.** Харнесс шлёт, роут превращает
  в `data-step`, консоль рисует. Добавил вариант в union — правь `writeStep` в роуте
  и разбор в `chat.tsx`, иначе шаг молча не появится в таймлайне: TypeScript поймает
  только первое из трёх, если разбор написан через `default`.
- **Мест, знающих внутренности SDK, ровно два:** `toolCalls.ts` (не-стрим) и
  `streamCoach.ts` (стрим). Третьего быть не должно.
- **`emitter.active` решает, стримить ли заход коуча.** Не-стрим путь обязан остаться
  обычным `run(...)` — по нему идут evals, replay и `/api/agent/run`. Сделаешь стрим
  безусловным — evals пойдут по непроверенному пути.
- **`review-done` шлётся после `enforceApproveThreshold`.** До неё в таймлайне встанет
  `approve`, который прогон не признал и который не открыл гейт.
- **`id` шага несёт префикс прогона.** Без него реконсиляция data-частей рискует затереть
  результат прошлого прогона в той же сессии.
- **Кнопка «в notion» — только на последнем одобренном плане.** `/api/plan/notion` сверяет
  текст с `data/output.md`, где лежит план последнего одобренного прогона; на старых
  сообщениях кнопка гарантированно даёт `409`.
- **Дублирование имён тулов никуда не делось.** `TOOL_LABELS`, `SEARCH_KNOWLEDGE`
  и `NOTION_CREATE_PAGE` переезжают из `agent-console.tsx` в `chat.tsx` вместе со своей
  причиной: консоль клиентская, серверные модули в неё не тянут.
- **`MIN_ROUNDS` / `MAX_ROUNDS` тоже переезжают** и остаются продублированными
  из `runHealthAgent.ts`. Меняешь там — меняй здесь.
- **Превью черновика троттлится.** Снимешь троттлинг — роут начнёт слать сотни килобайт
  на план в три килобайта.
- **`maxDuration = 300` в роуте.** Прогон идёт минутами; дефолтный потолок его обрежет.

## Проверка

```bash
npm run build          # сборка и типы — единственная автоматическая проверка в проекте
npm run dev            # живой прогон: таймлайн, стриминг плана, новая сессия
```

Живьём проверяются: таймлайн оживает по мере работы; ревизия видна отдельным шагом;
план стримится; вердикт и оценка стоят под планом; `needs_human_professional` показывает
карточку специалиста вместо плана; история прогонов остаётся в сессии; «новая сессия»
обнуляет чат.

`npm run eval` руками не гоняется без отдельной просьбы: пять походов в модель, десятки
минут и расход ключа. Его неизменность обеспечена по построению — при `onEvent === undefined`
`emitter.active === false`, и `runCoach` вырождается в тот же `run(...)`, что стоит
в цикле сейчас.
