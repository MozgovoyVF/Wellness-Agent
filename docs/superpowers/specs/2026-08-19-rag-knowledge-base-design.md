# RAG: база знаний, pgvector и retrieval-тул коуча

Дата: 2026-08-19 · статус: утверждён к реализации

## Зачем

У коуча сейчас два источника фактов, и оба про конкретного человека: профиль и дневник
(`data/`, через MCP) плюс личные рецепты (`data/recipes.md`). Всё остальное — что вообще
бывает за ужин, сколько белка класть, как строится неделя тренировок — он берёт из головы
модели. Это работает ровно до тех пор, пока не нужен воспроизводимый ответ: одна и та же
задача даёт разные рецепты, а проверить их источник нечем.

Задача — добавить **второй вид памяти**: общую базу знаний, из которой коуч достаёт
готовые куски текста по смыслу запроса, а не сочиняет их заново. Личная память при этом
остаётся ровно там, где была, — в markdown и за MCP.

Границы намеренно узкие: один embed, один similarity search, никаких фреймворков,
reranking, hybrid search и переписывания запроса.

## Memory vs RAG — концепция, которую воплощает дизайн

| | Личная память | База знаний |
|---|---|---|
| Что это | кто ты: цели, травмы, непереносимости, что ел вчера | что мы умеем: рецепты, правила питания, шаблоны, восстановление |
| Где лежит | `data/profile.md`, `data/log.md`, `data/recipes.md` | `knowledge/*.md` → Supabase |
| Как достаётся | целиком, точным чтением файла | по смыслу запроса, топ-K похожих кусков |
| Кто отдаёт | MCP-сервер `markdown-health` | локальный тул `searchKnowledge` |
| Меняется | каждый день, по одному человеку | редко, общее для всех |

**`data/recipes.md` остаётся и не переезжает.** Это не дубль `knowledge/recipes.md`, а его
противоположность: там — что человек правда готовит, здесь — что мы умеем предложить.
Промпт коуча обязан объяснить разницу явно, иначе он будет звать один тул вместо другого.

## Схема данных

SQL живёт в `docs/` нумерованными файлами, и номер задаёт порядок выполнения:
`001_create_knowledge_chunks_table.sql` и `002_create_knowledge_embedding_index.sql`.

```sql
create extension if not exists vector;

create table if not exists knowledge_chunks (
  id         bigint generated always as identity primary key,
  file       text        not null,   -- 'recipes.md'
  heading    text        not null,   -- текст ## заголовка
  content    text        not null,   -- тело секции без заголовка
  embedding  vector(1536) not null,  -- text-embedding-3-small
  created_at timestamptz not null default now()
);

create index if not exists knowledge_chunks_file_idx on knowledge_chunks (file);

-- ─── 002, выполнять ПОСЛЕ первого `npm run ingest` ──────────────────────────
-- ivfflat строится по данным: на пустой таблице кластеры пусты, и поиск начнёт
-- терять релевантные chunks. Отдельный файл именно поэтому.
create index if not exists knowledge_chunks_embedding_idx
  on knowledge_chunks using ivfflat (embedding vector_cosine_ops) with (lists = 4);
```

Решения и их причины:

- **`vector(1536)`** — размерность `text-embedding-3-small`. Она зашита в схему, и сменить
  модель эмбеддингов без пересоздания таблицы и полного переингеста нельзя. Это не
  недосмотр, а свойство pgvector: расстояние между векторами разных моделей не определено.
- **`lists = 4`, а не привычные 100.** Chunks будет 50–75 штук. `ivfflat` — приближённый
  индекс: он делит пространство на `lists` кластеров и смотрит только ближайшие. Сотня
  кластеров на семьдесят строк означает, что почти каждый список пуст, и поиск начнёт
  терять релевантные chunks. При таком размере Postgres, скорее всего, вообще выберет
  seq scan — и это правильный план: точный и мгновенный. Индекс здесь стоит ради урока
  и ради роста базы, а не ради скорости сегодня.
- **`ivfflat` создаётся после первого `ingest`.** Он вынесен в отдельный файл `002`
  именно поэтому: сперва выполняется `001`, потом заливаются данные, потом `002`.
  `if not exists` этого порядка не спасёт: индекс, созданный на пустой таблице, при
  повторном запуске будет молча пропущен и так и останется бесполезным.
- **RLS не включаем.** Ходим сервисным подключением из серверного кода, публичного доступа
  к таблице нет вовсе. Включённый RLS без политик просто закрыл бы таблицу и от нас.

## Модули

Новая папка `src/rag/` — по одной ответственности на файл, как в `src/harness/`.

| Модуль | Отвечает за |
|---|---|
| `chunks.ts` | `readKnowledgeChunks()` — разбор `knowledge/*.md` по `##`, метаданные `file` и `heading` |
| `embed.ts` | `embed(texts)` — один fetch в OpenAI-совместимый `/v1/embeddings` |
| `store.ts` | доступ к Postgres: `replaceChunks`, `matchChunks`, `closePool` |
| `retriever.ts` | `searchKnowledge(query, topK = 5)` — embed запроса → similarity → chunks |
| `retrievalLog.ts` | `createRetrievalLog()` — журнал обращений, по идиоме `gate.ts` |
| `searchKnowledgeTool.ts` | обёртка `tool()`: описание для модели, форматирование выдачи, запись в журнал |
| `index.ts` | что видно снаружи папки |

### Типы

```ts
export type KnowledgeChunk = { file: string; heading: string; content: string };
export type StoredChunk = KnowledgeChunk & { embedding: number[] };
export type KnowledgeMatch = KnowledgeChunk & { similarity: number };

export type Retrieval = {
  query: string;
  chunks: { file: string; heading: string; similarity: number }[];
};
```

### `chunks.ts`

Chunk = одна `##`-секция. Заголовок хранится отдельным полем и склеивается с телом
при эмбеддинге.

> **Правка после замеров на живой базе.** Изначально в вектор уходило всё тело секции —
> и на запросе «ужин с высоким белком без молочки» это давало ноль рецептов ужина
> в топ-5: длинный список граммов усредняет вектор и глушит заголовок. Вектор теперь
> собирается из заголовка и **первого абзаца**; в выдачу коучу по-прежнему едет секция
> целиком. Цифры — в комментарии к `embeddableText`. Следствие: первый абзац каждой
> секции обязан быть сводкой.

Текст до первой `## ` (то есть `# Заголовок файла` и вводные строки) в chunks не попадает:
это название документа, а не знание. Файл без единой `##` даёт ноль chunks — ингест
скажет об этом в лог, а не молча пропустит.

### `embed.ts`

```ts
export async function embed(texts: string[]): Promise<number[][]>
```

Один `fetch` на весь массив — API принимает батч, и делать N запросов ради 70 строк
незачем. `baseURL`, ключ и модель — из `.env`; порядок ответа сортируется по полю `index`,
а не берётся как пришёл (спецификация порядок не гарантирует).

Отсутствие `OPENAI_API_KEY` — понятная ошибка с текстом, что положить в `.env`, по образцу
`configureClient()` в харнессе.

### `store.ts`

Драйвер `pg`, SQL в коде — так оператор pgvector виден там, где его читают:

```sql
select file, heading, content,
       1 - (embedding <=> $1::vector) as similarity
  from knowledge_chunks
 order by embedding <=> $1::vector
 limit $2
```

`<=>` — косинусное расстояние; `1 - расстояние` даёт привычную похожесть, где больше =
лучше. Вектор уезжает параметром как строка `JSON.stringify(vector)` → `'[0.1,...]'`:
массив JS драйвер превратил бы в `{0.1,...}`, а такой литерал `vector` не принимает.

`replaceChunks(rows)` — **одной транзакцией**: `begin` → `delete from knowledge_chunks` →
многострочный `insert` → `commit`. Отсюда идемпотентность `npm run ingest`: повторный
запуск не создаёт дублей, потому что таблица каждый раз очищается. Транзакция нужна,
чтобы между удалением и вставкой не существовало момента, когда база пуста, а retriever
уже спрашивает.

Пул один на процесс, ленивый. `closePool()` зовёт только `scripts/ingest.ts` — скрипт
обязан завершиться; в Next пул живёт вместе с процессом сервера и закрывать его некому
и незачем.

### `retriever.ts`

```ts
export async function searchKnowledge(query: string, topK = 5): Promise<KnowledgeMatch[]>
```

Ровно два шага: `embed([query])` → `matchChunks(vector, topK)`. Никакой обработки запроса
до эмбеддинга и никакой пересортировки после — это прямой запрет из задачи, и нарушить
его легко «мелким улучшением».

### `retrievalLog.ts`

Повторяет форму `src/skills/gate.ts`: объект создаёт харнесс на прогон, тул получает его
замыканием и только пишет.

```ts
export type RetrievalLog = { record: (entry: Retrieval) => void; entries: () => Retrieval[] };
export function createRetrievalLog(): RetrievalLog;
```

**Почему журнал, а не разбор `newItems`.** Требование — видеть в трейсе сам запрос и
заголовки найденных chunks. Из `collectToolCalls` приезжают только имена тулов; чтобы
достать аргументы и выдачу, пришлось бы разбирать внутренние элементы SDK и парсить JSON
конкретного тула. `src/harness/toolCalls.ts` намеренно единственное место, где харнесс
знает про внутренности SDK, и размывать это ради одного тула не стоит. Гейт уже показал,
что «объект прогона передаётся в фабрику тула» — принятая здесь идиома.

### `searchKnowledgeTool.ts`

```ts
export function createSearchKnowledgeTool(log: RetrievalLog): Tool
```

Описание для модели (оно же интерфейс — правка описания меняет поведение агента ровно
как правка промпта): «ищи в базе знаний рецепты, правила питания, шаблоны тренировок,
правила восстановления».

Параметры: `query: string`, `topK: number` в диапазоне 1–10 с дефолтом 5.

Выдача модели — размеченный текст, где у каждого chunk видны файл, заголовок и похожесть:
без источника коуч не сможет сослаться на него в плане, а ревьюер — отличить знание от
выдумки.

**Ошибка базы не роняет прогон.** Нет `SUPABASE_DB_URL`, база недоступна, таблица пуста —
тул возвращает человекочитаемое сообщение («база знаний недоступна, опирайся на профиль,
дневник и рецепты») и пишет в журнал запись с пустым списком chunks. Причина та же, что
у `LOCKED_MESSAGE` в гейте: отказ инструмента — не ошибка агента, работу надо продолжить.
Ронять весь прогон из-за недоступного вспомогательного источника было бы обменом ценного
на служебное.

## Ингест

`scripts/ingest.ts`, запуск `npm run ingest`.

```
import './env'  →  readKnowledgeChunks()  →  embed(тексты)  →  replaceChunks(строки)  →  closePool()
```

Первым импортом — `./env`, как в `replay.ts` и `eval.ts`: вне Next `.env` читать некому,
а тела импортированных модулей выполняются раньше тела скрипта.

В лог печатается, сколько chunks нашлось в каждом файле и сколько строк уехало в базу:
ингест должен быть проверяем глазами, иначе «залилось» и «залилось правильно» неразличимы.

## Интеграция в харнесс

`src/harness/runHealthAgent.ts`:

1. Рядом с `createGate()` появляется `createRetrievalLog()` — один журнал на прогон.
2. Коуч собирается как
   `[...localCoachTools(gate), createSearchKnowledgeTool(retrievals)]`.
   **В `localCoachTools` тул не уезжает:** `src/skills/` — про markdown-данные человека,
   а retrieval это другая ответственность и другой источник. Что коучу доступно, и так
   решается в харнессе.
3. `HealthAgentResult` получает поле `retrievals: Retrieval[]`.

Гейт к RAG не применяется: тул только читает.

Ревьюеру и триажу тул не даётся — по тому же правилу, что и всё остальное: у контура
безопасности единственный результат обязан быть вердиктом.

## Трейс

`RunTrace` получает поле `retrievals: Retrieval[]`, `traceRun` кладёт туда журнал как есть.
Обрезать содержимое не нужно: в записи едут только заголовки и числа, тела chunks там нет.

`scripts/replay.ts` не правится — новое поле его не ломает, а сравнивать retrieval-запросы
двух прогонов построчно смысла не больше, чем сравнивать планы, которые он и так не
сравнивает.

## Промпт коуча v7

`prompts/healthCoach.v7.md` = v6 плюс раздел «База знаний», `ACTIVE_PROMPTS.coach → 'v7'`.

Что говорит новый раздел:

- **Сначала ищи, потом пиши.** Рецепт, правило питания, шаблон недели, приём восстановления —
  всё это есть в базе, и выдумывать их из головы не надо.
- **Разница между `list_recipes` и `searchKnowledge`.** Первый — что человек правда готовит
  (личное, короткий точный список). Второй — что мы умеем предложить (общее, поиск по
  смыслу). Оба уместны в одном плане: базовое блюдо из базы знаний, привычка — из личных.
- **Запрос формулируй по существу задачи**, вместе с ограничениями из профиля: «ужин
  с высоким белком без молочки» находит нужное, «ужин» — нет.
- **Не пересказывай выдачу.** Правило уже есть в v6 и распространяется на chunks: человеку
  нужен план, а не список найденного.

Имя тула в промпте — связь с кодом, как `read_profile` и `openmeteo_get_forecast`:
разъедется — коуч зовёт несуществующее и работает вслепую, а прогон не падает.

## Evals

`scripts/eval.ts`: `EvalCase.expect` получает необязательное поле

```ts
usedTools?: string[];   // эти тулы обязаны встретиться в result.toolCalls
```

Не задано — не проверяется, как и `minScore`. Провал печатается строкой вида
«не вызван тул searchKnowledge».

Новый кейс `evals/cases/knowledge-based-recipe.json`:

```json
{
  "name": "knowledge-based-recipe",
  "task": "Предложи ужин с высоким белком без молочки — сегодня после зала.",
  "expect": { "verdict": "approve", "minScore": 8, "usedTools": ["searchKnowledge"] }
}
```

Кейс проверяет **факт обращения**, а не текст плана: текст у модели каждый раз свой,
а «на такую просьбу агент обязан сходить в базу знаний» — свойство системы, и ломается
оно правкой промпта незаметно. Это ровно та же логика, по которой существует
`bad-medical-request`.

## База знаний

`knowledge/`, пять файлов, по 10–15 `##`-секций в каждом, содержание согласовано
с `data/profile.md` (правое колено, непереносимость лактозы, зал и гантели дома):

| Файл | О чём |
|---|---|
| `recipes.md` | блюда: состав с граммами, время готовки, белок, пометки «без молочки» |
| `nutrition_rules.md` | правила: белок на кг, сахар вечером, контейнер с собой, вода |
| `training_templates.md` | шаблоны недели и отдельных занятий, включая щадящие колено |
| `recovery_rules.md` | сон, разгрузочные дни, растяжка, поведение после переработки |
| `personal_preferences.md` | предпочтения по еде и режиму как общие паттерны, не медкарта |

Секции короткие и самодостаточные: chunk — единица выдачи, и половина мысли в нём
бесполезна. Никаких диагнозов, дозировок и БАДов — иначе база знаний станет способом
провести мимо ревьюера то, что он обязан заворачивать.

## Конфигурация

В `.env` добавляются три переменные:

```
OPENAI_API_KEY=sk-...
EMBEDDING_MODEL=text-embedding-3-small
SUPABASE_DB_URL=postgresql://postgres.<ref>:<пароль>@aws-0-<регион>.pooler.supabase.com:6543/postgres
```

Адрес берётся из Supabase → Connection string → Transaction pooler: прямое подключение
у Supabase только по IPv6 и работает не везде.

`DEEPSEEK_API_KEY` остаётся ключом **модели**; ключ OpenAI используется исключительно
для эмбеддингов. Смешивать их нельзя — это разные провайдеры с разными baseURL.

## Порядок запуска

```bash
# 1. выполнить docs/001_create_knowledge_chunks_table.sql в SQL Editor
# 2. залить базу знаний
npm run ingest
# 3. выполнить docs/002_create_knowledge_embedding_index.sql — теперь по данным
# 4. проверить
npm run build
curl -s -X POST http://localhost:3000/api/agent/run \
  -H 'Content-Type: application/json' \
  -d '{"task":"предложи ужин с высоким белком без молочки"}'
```

## Чего в этой работе нет

- фреймворков (LangChain, LlamaIndex) — прямой SQL и `fetch`;
- reranking, hybrid search, переписывания запроса — один embed, один поиск;
- переезда `profile`/`log` в базу — личная память остаётся в markdown и за MCP;
- тестов и TDD — по правилам проекта;
- MCP-сервера вокруг RAG (см. ниже).

## Осознанные отступления

**Тул локальный, хотя источник данных чужой.** По принципу из `CLAUDE.md` («стандартный
сервер стоит заводить там, где есть чужой источник данных») Supabase просился бы в MCP.
Против два довода: задача явно требует обычного тула, а журнал retrieval через границу
процесса не прокинуть — заголовки найденных chunks пришлось бы вытаскивать из выдачи
тула разбором текста. Требование «в трейсе видно, чем агент пользовался» жёстче, чем
симметрия слоёв. Отступление фиксируется строкой в `CLAUDE.md`, а не остаётся молчаливым.

**SQL лежит в `docs/` нумерованными файлами**, по постоянному правилу пользователя.
При обсуждении дизайна был выбран другой вариант — один файл в `supabase/migrations/`, —
но затем правило было подтверждено, и схема переехала в `docs/`. Папки `supabase/`
у проекта нет: два места для одного SQL разъезжаются молча, а это ровно тот класс ошибок,
который проект и так документирует десятком пунктов в «Что легко сломать».

## Что легко сломать (в `CLAUDE.md`)

- **Размерность вектора названа дважды** — `vector(1536)` в миграции и модель
  `EMBEDDING_MODEL` в `.env`. Сменил модель — пересоздавай таблицу и переингесть;
  иначе `insert` упадёт, а если размерность совпала случайно — поиск станет мусорным
  молча.
- **Имя `searchKnowledge` объявлено трижды**: в `searchKnowledgeTool.ts`, в `TOOL_LABELS`
  и в промпте `healthCoach.v7`. Плюс четвёртый раз — в кейсе eval. Расходится с промптом —
  коуч зовёт несуществующее; расходится с `TOOL_LABELS` — строка в трейсе теряет подпись.
- **Заголовок `## ` — граница chunk.** Поменяешь разметку в `knowledge/*.md` (например,
  уйдёшь на `###`) — ингест соберёт файл в один гигантский chunk или в ноль, и ни сборка,
  ни прогон этого не заметят: заметно только по числу строк в логе ингеста.
- **`retrievals` и `toolCalls` сопоставляются по порядку.** Если тул начнёт писать
  в журнал не на каждый вызов (например, «не логировать пустую выдачу»), нумерация
  в консоли поедет и запрос встанет напротив чужого вызова.
- **`npm run ingest` — разрушающая операция.** Он удаляет всё содержимое
  `knowledge_chunks` и заливает заново. Это и есть требуемая идемпотентность, но запускать
  его против общей базы вслепую не стоит.

## Проверка

Полную DoD проверить в этой сессии нельзя: `npm run ingest`, живой retrieval и evals
требуют проекта Supabase и ключа OpenAI. В сессии доводим до `npm run build` — единственной
автоматической проверки проекта — и до `npm run mcp:inspect`, который должен продолжать
показывать прежнюю картину (RAG в MCP не лезет). Остальное выполняется по разделу
«Порядок запуска» и сверяется с DoD.
